# 세부 평가 기준과 역할별 평가자 입력

## 0~5점 채점

현재 점수 계약은 score-0-5-v2, 평가자 버전은 openai-judge-1.12, 역할 기준은 role-rubric-2.5이다. 26개 항목 ID와 점수 경계를 유지하며 A3-03의 담당과 범위는 아래 2.5 설명으로 변경한다. 각 항목의 5점 기준은 해당 통과 조건 전체와 필수 증거 충족, 0점 기준은 해당 실패 조건에 해당하면서 핵심 목적에 반하거나 실제 수행 범위 전체가 불충족한 경우다. 1~4점은 해당 항목의 목적에 대한 부족 정도로 설명하며 문장 수를 세지 않는다. 코드의 scoring_anchors와 항목별 정상/위반 예시를 함께 전달한다. 중간 점수의 사람 교정은 아직 남아 있다.

2.4는 TC-R05의 제목·통과/위반 조건·예시를 ‘요청 조건의 검증 범위 충족’으로 통일한다. 정상 상태 전환·조회도 요청과 TC를 대조하고, 범위 제한에 필요한 경계·명시된 범위 밖 처리 검사는 유지한다. 자료 부족은 REVIEW이며 정상 전환이라는 이유로 점수를 자동 부여하지 않는다. 기존 2.3 실제 평가의 비적용 오판은 보존하고, 새 안내의 실제 모델 효과는 미검증이다.

2.3은 TC-R05의 정상 범위도 평가한다는 점과 A4-02의 분류 대상 존재 조건을 명확히 한다. 경계 시험이 없다고 정상 조건 대조 전체를 비적용하지 않는다. 원본에 실패·정보 부족·오류·미실행 신호가 있거나 보고가 원인을 주장하면 원인 분류를 평가하며, 원본도 모두 정상이고 원인 주장도 없을 때만 비적용이다. 그 여부를 확인할 자료가 부족하면 REVIEW다. 이는 평가 AI에게 전달하는 기준이지 점수/판정 자동 보정 함수가 아니다.

`context`와 `artifact`는 같은 내용이어도 원문을 직접 보여준다. 다른 자료의 반복 이력은 동일 값의 참조로 줄이되 누락·잘못된 값·순서를 올바른 upstream으로 교체하지 않는다. 구조화 복원 확인은 ER 읽기 위치와 `OBSERVED_BASELINE`의 연결로 대조하고, 명세·계획·코드·실제 증거의 책임을 구분한다. TC에서 확인이 실제 빠졌다면 여전히 지적한다. 전송 한도·출처·점수 경계·호출 상한·사람 승인 보호는 유지하며 새 패킷/Preview와 별도 승인 없이 실제 평가를 반복하지 않는다.

| 점수 | 판단 기준 |
|---|---|
| 5 | 필수 기준 전체를 근거로 확인 |
| 4 | 핵심 충족. 결과·재현성·안전에 영향 없는 경미한 설명 부족 |
| 3 | 핵심 일부 충족이나 중요한 누락이 확인됨 |
| 2 | 일부만 충족하고 주요 조건 여러 개가 누락·불일치 |
| 1 | 핵심 대부분 미충족으로 목적 달성이 어려움 |
| 0 | 핵심 목적에 반하거나 수행 범위 전체의 불충족이 확인됨 |
| 미평가 | 판단 근거 부족. 숫자 0과 구분 |
| 해당 없음 | 실제 적용 대상이 아니라는 근거가 있음 |

자료가 없다는 사실만으로 0점을 주지 않는다. 위반 여부를 확인할 수 없으면 판단을 보류한다. 반면 미실행이 확인된 자료에서 실행·복원을 완료했다고 주장하면 그 주장과 기록의 불일치를 평가한다. 미실행 자체를 무조건 0점으로 처리하는 것은 아니다. 과거 점수와 이유는 당시 기록으로 보존한다.

점수와 PASS/FAIL은 함께 보존한다. 새 v2는 PASS 4~5점, FAIL 0~3점이다. 필수 위반이 있으면 경미한 부족이라는 4점 설명과 양립하지 않는다. 과거 v1의 4점 FAIL은 그 버전대로 읽고 바꾸지 않는다. REVIEW/NOT_APPLICABLE은 null이며 증거 부족을 0점 또는 만점으로 환산하지 않는다. 높은 평균은 위반 판정·코드 검사 FAIL·사람 승인 보호를 덮지 않는다. 점수로 프로젝트 1의 Checkpoint나 실행 분기를 바꾸지 않는다.

대시보드는 평가 n/26항목·미평가 수를 먼저 표시하고, 평가된 항목 평균 /5와 위반을 함께 보여준다. 100점 환산 필드는 기존 결과 호환용으로 유지하며 전체 정확도·완성도가 아니다. COMMON과 E2E는 Agent별 점수에서 분리한다. C01/C02를 네 역할이 평가한 경우 네 점수가 모두 있어야 최저점을 한 번만 반영한다. 하나라도 미평가면 공통 점수도 미평가이며 확인된 위반 경고는 유지한다. 2회 이상이고 채점 버전·채점/비적용 항목 구성이 같을 때만 회차 평균·최저점을 표시한다. 점수의 일치는 의미 일관성이나 통계적 안정성 증명이 아니다.

새 집계 보완은 점수 척도뿐 아니라 기록된 역할 기준 버전·평가자 버전·평가 모델도 대조한다. 알려진 버전이 섞였으면 묶음과 그룹 평균만 무점수로 두고 항목별 원본 점수·FAIL 경고·수량은 유지한다. 버전이 빠진 과거 기록은 표시용 항목 평균을 유지할 수 있지만 반복 평균 비교에는 넣지 않는다. 과거의 `rubric_coverage.profile`이 명시한 역할 기준은 그대로 읽으며, `custom`을 기준 버전으로 추측하지 않는다. 새 scored Judge와 파이썬 사실 채점에는 실제 canonical 기준 버전을 기록한다. 화면에는 비교 보류 설명만 제공하며 원본 버전·모델 문자열은 공개 API 응답에서 제외한다. 이전 저장 결과를 새 버전으로 다시 쓰지 않는다. 저장 응답 대조와 로컬 회귀 검사에서 혼합 평균 차단·같은 버전 비교·원본 FAIL 보존을 확인했다. 공개 응답의 비공개 처리 전에 원본 버전으로 비교하며, 같은 모델과 다른 모델의 두 회차 대조도 로컬로 확인했다. 이는 실제 모델 의미 판정의 정확도나 브라우저 실화면 검증이 아니다. 상세 결과는 인계 문서에 있다.

새 full-flow의 기존 네 역할 평가에 점수를 추가하며 호출 수를 늘리지 않는다. 개별 judge-openai는 --role-rubric --score-rubric으로 적용한다. 기존 판정만 있는 Run은 숫자로 변환하지 않는다. 변경된 지침·응답 계약은 새 Preview 승인이 필요하며 이전 승인을 재사용하지 않는다.

E01~E04도 점수 기준이 있지만 네 역할 평가만으로 점수를 만들지 않는다. E2E packet과 --role-rubric --score-rubric을 사용한 별도 근거 평가가 가능하다. full-flow는 E04의 무승인 변경 위반은 로컬 기록으로 표시하지만, 자산이 그대로라는 사실만으로 승인 전후 절차 전체를 5점으로 만들지 않는다. E01~E03의 자동 모델 호출·승인 후 전 과정 검증은 아직 없다. 실제 모델의 점수 품질·사람 채점과의 일치율도 미검증이다.

## 평가 담당과 정답 근거

분담은 파이썬 중심 4개·AI 중심 12개·혼합 10개다. 26개 모두 평가 완료됐다는 뜻이 아니다. 2.5부터 A3-03은 코드 품질 읽기가 아니라 계획과 실제 검사 기록의 대조로 범위를 고정한다. 생성기 구현·허용 수정 범위·호출 상한은 P1 로컬 회귀검사와 기존 로컬 호출 예산 검사에서 별도로 확인한다.

| 담당 | 항목 | 확인 방법·남은 경계 |
|---|---|---|
| 파이썬 | A3-03 | 신규 TC 번호·계획·구조화 관찰값·결과 대조. 같은 실행·대상·기대값·관찰 순서·일치 여부와 연결 해시 확인. 코드 생성 구현·복원 전체 품질을 이 점수 하나로 평가하지 않는다. 기록 없음·중단·지원하지 않는 과거 알림 비교는 REVIEW다. |
| 파이썬 | A4-01, A4-03 | full-flow-0.6에서 상태·제품/환경/고정 사례 수량과 Run/TC/요구사항/출처·상태·보고 체인·증거 해시를 대조한다. A4 모델 입력에서는 두 항목을 제외한다. 화면 의미나 원인 분류를 해시로 판정하지 않는다. |
| 파이썬 | E04 | 현재 full-flow는 공식 승인을 수행하지 않는다. 무승인 자산 변경은 FAIL, 변경 없음만으로는 전체 승인 절차 REVIEW다. 승인 후 등록까지 자동 PASS하는 평가기는 만들지 않았다. |
| AI | A1-01~04, A2-01, TC-R01~07 | 요청·SRS·작성 기준·기존 TC와 산출물의 의미를 대조한다. 문장 길이나 특정 표현을 정답으로 하지 않는다. |
| 혼합 | C01~02, A3-01·02·04, A4-02·04, E01~03 | 파일/값/실행 사실은 기존 코드 검사, 의미의 적절성은 모델/사람 판단으로 구분한다. 모든 세부 질문의 자동 파이썬 검사가 구현된 것은 아니다. E01~03은 별도 전체 자료 평가가 필요하다. |

파이썬의 확정 사실 항목은 5점 충족/0점 불일치로 표시한다. 부분 점수를 임의로 만들지 않으며 자료 부족·해석 불가는 REVIEW다. A3-03의 제품 불일치 검출 자체는 감점 사유가 아니다. 단독 judge-openai의 --role-rubric과 full-flow 모두 프로그램 담당 항목을 AI 입력에서 제외한다. 전체 기준 정의는 26개를 유지하며 과거 AI 점수·평가 방식은 그대로 읽는다.

정답 근거는 입력 요청·그 실행의 SRS·사용자 TC 작성 기준·독립 실행/승인 기록이다. 프로젝트1 Checkpoint PASS나 프로젝트1의 실패 라벨을 그대로 정답으로 복사하지 않는다. 앞 단계 출력을 그대로 평가하되 그 출력의 타당성도 원문에 대조한다. 사람 확인 전 사례 기준은 DRAFT이며 충돌·불명확은 REVIEW다.

### 자료 수집과 비용

A3/A4에는 해시를 확인한 stdout/stderr를 제공하고 자동화 코드 본문은 기본 모델 입력에서 제외한다. 코드 식별 해시와 의도적 제외 표시(LOCAL_ONLY_CODE)는 남으며 코드가 크다는 이유로 로그 전송 용량을 먼저 소비하지 않는다. 로컬 코드 조사용 수집 옵션은 유지하지만 실제 AI 연결 수집기는 항상 코드 본문을 제외한다. 로그별 24,000바이트·지원 근거 40,000바이트 제한과 민감정보 검사는 유지한다. 역할별 평가 JSON 본문은 근거 번호를 붙인 후 UTF-8 기준 최대 250,000바이트이며 프로젝트 자체 예산이다. 모델 토큰 한도와 동일하지 않다. Preview에서 본문/한도/요청 크기를 확인하며 초과 시 자동 절단·추가 호출하지 않는다. 중복은 동일 내용의 원문 참조로만 묶고 context/artifact 직접 대조 자료는 유지한다. 전체 HTML·이미지·영상은 전송하지 않는다. 코드 미전송은 실행 근거 부족과 같지 않지만 실제 로그도 없다면 판단을 보류한다.

v2 전송은 항목별 통과/위반 조건을 rubric에 한 번만 넣고 공통 0~5점 설명을 scoring_scale로 공유한다. 원문 자료·개별 조건·판정 목적은 바꾸지 않는다. 이 중복 제거 후에도 큰 자료는 기존 한도에서 차단되며, 자료 누락을 자동 요약으로 숨기거나 한도를 늘리지 않는다.

### 평가기 자체 비교

judge_calibration.examples.json의 개발 사례는 A1 값/미정 정보, A2 조작/근거/복원 및 SRS 개정 필요성·미변경 조건 보존, A3 제품 FAIL과 Agent 실패 구분, A4 원인 과장, E2E 정보 부족 전달을 비교한다. 기대 판정과 점수는 모델 입력 sources에서 제외한다. 모두 DRAFT이며 사람이 확인한 정답이 아니다. 현재 모의 전송 검사로 실제 모델의 의미 정확성을 주장하지 않는다. 후속 실제 응답을 사람 판단과 비교해야 한다.

이번에는 새 모델·프레임워크·추가 호출 단계를 도입하지 않았다. 참고한 공개 자료:

- [OpenAI 평가 지침](https://developers.openai.com/api/docs/guides/evaluation-best-practices): 작업별 기준과 사람 판단 대조를 적용. 점수 자체를 정확도로 해석하지 않는다.
- [Anthropic Agent 평가 사례](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents): 코드·모델·사람 평가를 역할에 맞게 조합하고 결과와 실행 기록을 구분한다.
- [LangChain 평가 방식](https://docs.langchain.com/langsmith/evaluation-types): 구조·사실 확인과 의미 평가를 나누고 저장 사례 비교를 활용한다. 해당 서비스 설치나 외부 전송은 하지 않았다.

기준 버전: `role-rubric-2.5`. 기존 23개 상위 역할 분류와 26개 세부 항목을 유지합니다. TC-R06은 TC 근거와 SRS 개정 필요성·전체 인수기준 셀의 미변경 조건 보존을 함께 평가합니다. 정의 파일은 [detailed_rubric.py](../src/eval_harness/detailed_rubric.py)입니다. 점수 척도는 score-0-5-v2를 유지하며 과거 기준의 판정은 보존합니다.

재사용 분기 확인은 유지합니다. 신규 TC 없음·관련 기존 TC·신규 계획 불필요 기록이 함께 있을 때 AI 담당 A3-01·A3-02는 `NOT_APPLICABLE`이며 실제 시험·복원을 보는 A3-04는 면제하지 않습니다. 현재 프로그램 담당 A3-03은 신규 TC·계획·관찰 기록의 대조가 없으면 `REVIEW`로 남깁니다. 재사용 시험의 실패나 0점이라는 뜻은 아닙니다. 새 평가는 현재 `role-rubric-2.5` 패킷과 새 Preview가 필요하며 과거 패킷·판정·점수는 다시 쓰지 않습니다.

저장 평가와 전체 실행은 `handoff_checks`로 정보 부족을 A1·A2·실행·분석·보고까지 대조합니다. 질문은 실행·분석·보고의 원문 또는 `사용자 확인 요청: ` 접두어를 제외한 원문이 같아야 합니다. 임의 문장 유사도를 사용하지 않으며 CP1/CP2의 추가 안내는 질문 목록과 구분합니다. 전달 자료가 없거나 형식을 읽을 수 없으면 NOT_EVALUATED입니다. 집계/연결 채점에 필요한 자료가 없으면 REVIEW이며 빈 목록·0건으로 대신하지 않습니다.

별도 V1 Fixture 검사 `A2-INVARIANT-001`은 승인 TC 전체에서 불변 검증 항목의 존재만 확인합니다. 비어 있으면 누락인지 정당한 비적용인지 `ABSTAIN`으로 남기며 자동 통과시키지 않습니다. 항목이 있다는 사실이 내용의 타당성을 보장하지는 않습니다. V1 A4 집계 검사는 원본 실행 행의 상태별 수량을 다시 계산합니다. 이 규칙 검사들을 V2의 전체 의미 평가로 설명하지 않습니다.

**항목을 정의하고 평가자 입력에 연결한 것과 실제 모델 평가가 정확하다는 것은 다릅니다.** 현재 자동 검사는 프로필 무결성·필수 자료 키 존재·출력 계약 검사입니다. 실제 의미 평가, 사람 정답과의 교정, 전체 프로젝트 1 반복 실행은 별도 검증이 필요합니다.

현재 주 시험은 [FLOW-v1.0](11_RELIABILITY_EVALUATION_PLAN.md)의 **전체 흐름 5회·매 회차 A1~4 및 Checkpoint·연결 평가**입니다. 단독 역할 패킷은 그 평가의 구성요소이지 전체 시험의 대체물이 아닙니다. 아래 Agent 2 예시를 ‘Agent 2만 먼저 실행하는 계획’으로 해석하지 않습니다.

PREVIEW/DRY_RUN은 안내 작성 근거이지 전송·수신·공식 승인 완료 근거가 아니다. 안내 자료 미확보는 판단 보류이며 P1 전체에 안내가 없다는 증거가 아니다. 빈 확인 목록 자체를 감점하지 않고 실제 필요한 질문·다음 행동의 누락을 평가한다. TC-R01~06은 이미 받은 사용자 TC를 기준으로 합니다. TC-R07은 기존 프로젝트 복원 계약입니다. 예시의 온도·색상·버튼 클릭 횟수를 모든 요구사항에 강요하지 않습니다. 읽기 전용 TC는 근거를 들어 복원 해당 없음이 될 수 있습니다. 준비 동작마다 제품 기대결과를 억지로 추가하지 않습니다.

예를 들어 온도 표시만 요청했다면 알림 색상 미정 때문에 실패시키지 않습니다. 반대로 알림 색상 변경을 요청했는데 목표 색상이 없다면 그 값만 질문합니다. 대상이 안전하게 분리 가능할 때만 확정된 부분을 진행합니다.

## 3. 역할별 전체 기준으로 Preview 만들기

```bash
python -m eval_harness judge-openai --packet benchmarks/v2/role_packet.example.json --model MODEL_ID --role-rubric
```

- API 키나 외부 호출 없이 Preview를 생성합니다. 모델 ID는 사용자가 선택하며 이번 변경으로 모델을 바꾸지 않습니다.
- 기존 패킷의 `rubric`을 해당 Agent의 공통+역할 기준으로 교체합니다. A1 6개, A2 10개, A3 5개, A4 4개입니다. Agent 4는 규칙 기반 분석기 산출물을 평가하는 것이며 생성 Agent로 바꾸지 않습니다.
- A1~A4 단일 역할 호출에는 E01~E04를 섞지 않습니다. E2E 역할 패킷은 별도로 지원하지만 full-flow가 E2E 모델을 자동 호출하지는 않습니다.
- `--role-rubric` 없는 기존 호출은 호환성을 유지하며 `CUSTOM_SUBSET`으로 표시합니다. 일부 항목 평가를 전체 Agent 평가로 표현하지 않습니다.
- 역할 프로필로 선언한 항목의 누락·내용 변경·다른 역할 혼입을 거부합니다. 원본 파일은 바꾸지 않으며 프로필 적용 후 Preview 해시가 달라집니다. 예전 해시로 실행할 수 없습니다.
- 실제 실행은 별도 사용자 승인과 Preview에 맞는 `--execute --approval-sha256 ...`가 필요합니다. 호출·재시도 한도와 비밀정보 검사는 유지합니다.

### 필요한 자료

| sources 키 | 내용 |
|---|---|
| context | 원래 요청·SRS·해당 회차 실제 앞 단계 출력·기존 TC·역할 및 별도로 구분한 독립 판정 기준 |
| artifact | 이번에 평가할 해당 Agent 산출물 |
| trace | 실제 전달·조작·계획/코드·수정 이력 등 해당 기준을 확인할 기록 |
| inventory | 당시 UI 요소·표시·활성 상태·허용 행동 근거 |
| execution | 실제 실행 행·관찰·복원·화면/로그 등 검토에 필요한 증거 내용 |
| approval | 전체 흐름의 유효한 승인·자산 변경 기록; 현재 단일 역할 프로필에서는 사용하지 않음 |

모든 키를 모든 역할에 강요하지 않습니다. 항목별 `evidence_requirements`로 구분합니다. 단독 `judge-openai`는 사람이 자료를 선정합니다. `full-flow`는 실제 회차의 역할별 요청·출력·검사·계획/코드·실행 JSON을 수집하며 로컬 작업 경로 치환을 기록합니다. 전체 HTML·화면·Trace는 전송하지 않고, 남은 민감 패턴이나 크기 초과는 전송 전 차단합니다.

전체 연결기에서는 실제 앞 단계 출력을 보존해야 합니다. 잘못된 분석을 검토된 정답으로 교체하면 실제 오류 전파를 평가할 수 없습니다. 평가자에게 전달한 독립 정답·평가 의견은 프로젝트 1의 생성 입력으로 다시 보내지 않습니다.

예시 패킷에는 실제 전달 이력 `trace`가 없습니다. 따라서 공통 2개는 `MISSING_EVIDENCE`, TC 관련 8개는 `READY_FOR_REVIEW`입니다. 후자는 자료 키가 있다는 뜻이지 의미 평가 합격이 아닙니다. 빈 값·빈 목록·빈 객체도 증거 누락으로 봅니다. 비어 있지 않은 내용의 진실성·충분성은 별도 검토가 필요합니다.

필수 자료가 없을 때 AI가 PASS나 NOT_APPLICABLE을 반환하면 출력 계약 오류로 처리합니다. 이는 Agent의 오답 확정이 아니라 평가자의 잘못된 판정 형식입니다. 근거 부족은 REVIEW, 현재 자료로 명확히 확인되는 위반은 FAIL로 남길 수 있습니다. 인용 존재 검사만으로 판단의 논리적 정확성을 보장하지 않습니다.

## 4. 정상·오류 대조와 평가기 검증

- 26개 항목 각각의 정상/실패 예시를 정의했습니다. 이 52개 짧은 예시는 기준 설명용이며 독립된 Live Benchmark나 사람 정답으로 확정한 결과가 아닙니다.
