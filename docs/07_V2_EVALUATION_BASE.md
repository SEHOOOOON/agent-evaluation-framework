# 프로젝트 2 · QA Agent Evaluation Engineering

> 현재 목표·구현 순서는 [신뢰성 검증 계획 FLOW-v1.0](11_RELIABILITY_EVALUATION_PLAN.md)을 따릅니다. **주 시험은 전체 흐름 5회이며 매 회차 A1~4·Checkpoint·단계 연결을 각각 평가합니다.** 이 문서는 초기 저장 기록 검사 베이스의 기록입니다. 아래 당시 구현·설계 목록을 최신 전체 실행 기능이나 우선순위로 해석하지 않습니다.

기준일: 2026-09-19 · 구현 베이스 0.3

[역할별 상세 평가 명세와 자료 기법 적용 현황](08_AGENT_EVALUATION_SPEC.md)을 추가했습니다. 현재 자동 검사의 근거와 미평가 전문 항목을 구분해 보고합니다.

## 1. 무엇을 만드는가

**프로젝트 1의 QA Pipeline이 요구사항을 바꾸거나 실패를 숨기지 않고 일하는지, 독립된 기준과 실행 증거로 평가합니다.**

프로젝트 1은 QA 업무를 수행하고, 프로젝트 2는 그 수행 품질을 평가합니다. 기존 V1 Fixture 평가기는 보존하며 새 평가 대상은 `qa-agent-pipeline-v2`입니다. V1의 고정 Workflow Prototype과 실제 모델을 사용하는 V2를 같은 실행 방식으로 표시하지 않습니다.

초기 작성 당시에는 요약문을 참고했습니다. 9월 19일 교육 PDF·영상 일부 검토는 [과거 재평가](09_PROJECT1_REVIEW.md), 이후 전체 음성 자동 전사 검토와 화면 대조 범위는 [세부 기준](12_DETAILED_RUBRIC.md)에 구분했습니다.

## 2. 원안에서 실제 구조에 맞게 바꾼 점

| 원안의 표현 | 적용할 정의 |
|---|---|
| Checkpoint 승인 | 프로그램의 자동 검사 통과. 사람의 공식 SRS·TC 승인은 별도 |
| Agent 4 LLM 원인 추론 | 현재 Agent 4는 규칙 기반 분류기. 중립 신호와 사람이 정한 분류 정답으로 평가 |
| 제품 시험 FAIL → 평가 FAIL | 실패를 올바르게 발견·보고했다면 해당 Agent 행동은 성공일 수 있음 |
| HTTP 500이면 제품 결함 | 그 신호만으로 제품·환경 원인을 단정하지 않음 |
| 30개 × 1회 결과로 신뢰성 증명 | 개발·교정·보류용 데이터와 반복 Trial을 분리. 초기 결과는 제한된 관찰 |
| 과거 Run을 현재 Baseline 결과로 비교 | 평가 시점 코드와 당시 생성 코드 구분. 당시 commit 미기록은 unknown |
| CP PASS를 정답으로 사용 | 입력·TC·실행 행·증거를 독립 대조. CP 결과를 그대로 재채점하지 않음 |
| 기존 TC가 있으면 무조건 수정 우선 | V2의 기존 TC 선택 + 변경분 후보 방식 사용. 이름보다 실제 검증 범위 비교 |

## 3. 당시 구현한 저장 검사 베이스

```text
깨끗한 V2 Git 기준 + 기존 Run 3개
              ↓ 읽기 전용
Baseline: commit · 파일 해시 · 당시 Prompt/Model/계약
              ↓
독립 코드 검사 → JSON 결과 + HTML 보고서
              ↓
FAIL / ERROR / REVIEW → 사람이 의미·정답 기준 검토
```

- 실행: `python -m eval_harness run-v2 --target ../qa-agent-pipeline-v2`
- 데이터: `benchmarks/v2/recorded_v1.jsonl`
- 구현: `src/eval_harness/v2_recorded.py`
- 출력: 새 `evaluation-runs/V2-EVAL-.../`의 `baseline.json`, `result.json`, `report.html`
- 출력은 대상 V2 저장소 밖에만 저장합니다. 실행 전후 원본 해시와 Git 상태를 대조합니다.
- 현재 모드는 **RECORDED_REVIEW**입니다. 새 모델 호출·제품 실행·Notion 게시·공식 등록 모두 하지 않습니다.
- 초기 저장 검사에는 Live Adapter·Judge·버전 비교·대시보드 통합이 없었습니다. 이후 단일 역할 Judge 호출 경로와 저장 V2 평가를 조회하는 대시보드가 구현됐습니다. 전체 실행 연결기는 이후 무과금 검증됐지만 실제 Live·사람 교정은 미실행이며 [구현 매핑](05_IMPLEMENTATION_MAPPING.md)을 따릅니다. HTML 보고서도 직접 열 수 있습니다.

평가 시점 코드가 과거 Run을 생성했다고 가정하지 않습니다. 당시 실행 commit이 없는 Run에는 `execution_commit=null`을 기록합니다. Agent 1·2·3의 저장 manifest에서 model/prompt/contract를 수집하며 없던 값을 현재 기본값으로 보충하지 않습니다.

## 4. Agent별 성공 기준과 구현 범위

| 대상 | 성공의 정의 | 현재 자동 확인 | 사람/Judge 또는 후속 구현 |
|---|---|---|---|
| Agent 1 | 요청 의미 보존, 확정·미정 구분 | 조건 ID, 인용 근거 존재, 입력/출력 해시 | 의미 반전·영향 누락·과잉 확장 |
| Agent 2 | 기존 검증 대조와 필요한 상세 TC 설계 | TC 중복 ID, 사전조건/단계/기대결과 존재, 조건 연결, 지원 사례의 판정 시점 | 재사용 적절성, 독립성·복원·경계 조건의 충분성 |
| Agent 3 | TC를 보존한 계획과 실행 가능한 코드 | 후보 코드 해시·Python 구문, 증거 파일·해시, 종료 코드 | Selector 적절성, 조작 의미 보존, 실제 재시험 |
| Agent 4 | 중립 실행 신호를 일관되게 분류·보고 | 원본 행 재집계, 예상 분류/최종 권고, 실행→보고 해시 | 원인 정답 교정, 애매한 오류의 원인 검토 |
| E2E | 확정 범위 수행과 미해결 사항 분리 | 정보 부족 전달, 결과 분포·보고 일치 | 전체 조건 Coverage, 승인 권한과 자산 변경의 인과 검증 |

해시 일치는 **보존된 자료가 일치한다**는 의미이지 내용이 옳다는 증명은 아닙니다. Python 구문 통과도 시험 실행 성공이 아닙니다. 코드 검사로 표현 품질 전체를 평가했다고 주장하지 않습니다.

0.2에서는 각 기대결과의 빈 문장·개별 근거 누락, 신규 후보 실행에 대응하는 TC 설계 누락, 검토 항목의 테스트 ID·상태·증거 불일치, 정보 부족 원문 변경을 검사합니다. 기존 TC만 재사용한 실행에는 신규 설계를 강요하지 않습니다. 필수 증거 종류의 완전성, 전체 Coverage와 문장 의미 평가는 여전히 미구현입니다. 지원하지 않는 중첩 자료 형식은 ERROR이며, 사례의 필수 Manifest 오류는 다른 사례 결과와 함께 기록합니다.

## 5. Critical Gate와 판정

| 상태 | 의미 | CLI 종료 코드 |
|---|---|---:|
| FAIL | 인용 조작·결과 모순·증거 변조 등 현재 자동 기준 위반 | 2 |
| ERROR | 필수 자료 누락, 지원하지 않는 계약, 평가 실행 오류 | 4 |
| REVIEW | 자동 검사 위반은 없지만 의미·사람 검토가 남음 | 3 |
| PASS | 최종 평가 통과 | 현 베이스에서는 발급하지 않음 |

Critical FAIL이 있으면 이후 ERROR나 좋은 점수로 덮지 않습니다. 모든 검사 결과는 보존합니다. 원본 자체가 없거나 설정이 잘못되면 실행을 중단합니다. 지원하지 않는 스키마를 Agent 실패로 단정하지 않습니다.

품질 점수·Agent 통과율·반복 안정성은 null 또는 미측정입니다. `oracle_status=DRAFT`는 AI가 작성한 평가 기준 초안이며 사용자 검토 완료를 뜻하지 않습니다. 나중에 HUMAN_REVIEWED가 되어도 자동 검사만으로 의미 평가 완료가 되지는 않습니다.

## 7. Judge·사람 검토 설계의 현재 해석

초기 베이스 당시에는 Judge 호출기가 없었습니다. 현재 별도 단일 역할 호출·프로필·출력 검사는 구현됐지만 사람 정답 교정·전체 반복 통합은 미완료입니다. 정답 조건은 대상 Agent 입력에 노출하지 않고, 평가용 패킷에만 독립 기준과 해당 회차 입력·산출물을 포함합니다.

초기 평균 4점·개별 3점 제안은 채택하지 않았습니다. 현재 [역할별 세부 기준](12_DETAILED_RUBRIC.md)에 따라 A1~4의 충족·위반·증거 부족을 분리하며 TC 상세도만으로 전체 성능을 대표하지 않습니다. 미교정 점수로 합격을 발급하지 않습니다.

각 seed를 사람이 독립 검토하고 `human_review.template.json`에 판단·근거·검토자를 기록합니다. Judge와 불일치하면 Agent·Dataset·Evaluator·환경을 구분해 조사합니다. 사용자 TC 예시는 상세도 Rubric의 근거로 쓰되 없는 제품 기대값을 추가하는 정답으로 사용하지 않습니다.

## 8. 이전 구현 제안의 대체

초기의 A1·A2 우선 연결·중요 사례 3회 제안은 현재 주 시험의 순서가 아닙니다. **전체 A1~4 실행·수집·평가 연결 → 무과금 검증·독립 정답 준비 → 승인 후 전체 경로 리허설·교정 → 동일 조건 전체 흐름 5회**로 정리했습니다. 단독 시험은 발견 문제의 원인 분리에 사용합니다.

현재 순서와 종료 조건은 [실행 계획 7절](11_RELIABILITY_EVALUATION_PLAN.md#7-현재-구현과-다음-순서)을 따릅니다. 원본 보호·정답 검토·개발/보류용 분리·같은 조건의 버전 비교 원칙은 유지합니다. 서로 다른 날짜와 요청의 저장 Run 3개를 개선 전후나 반복 시험으로 계산하지 않습니다.
