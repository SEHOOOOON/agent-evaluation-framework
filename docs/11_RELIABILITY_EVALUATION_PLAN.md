# 프로젝트 2 · 프로젝트 1 신뢰성 검증 계획

기준일: 2026-10-05 · 계획 버전: `FLOW-v1.0` · 현재 구현: `full-flow-0.13`

P1/P2 값 비교의 로컬 대조 테스트는 `QA_P1_TEST_ROOT`에 P1 checkout을 지정해 실행한다. 지정하지 않은 독립 P2 테스트 환경에서는 해당 저장소 간 대조만 skip하며 성공으로 세지 않는다. 새 P1 자동화와 P2는 true/1을 구분하고 같은 int/float 수치는 허용한다. 과거 실행을 새 기준의 성공으로 변경하지 않는다.

연결 실행은 P1 결과 수집 후 이번 예산으로 평가할 모든 역할의 입력을 먼저 점검하고 Judge 호출을 시작한다. 입력 크기·민감정보 등 준비 실패는 `JUDGE_PREFLIGHT_FAILED`로 남기고 해당 묶음의 Judge를 호출하지 않는다. 이미 수행된 P1 생성 비용과 별개이며, 예산 밖 역할은 미평가다. 코드 본문은 실행 또는 최종 생성 기록의 해시와 대조하는 공통 수집기만 사용한다. 중복 참조도 각각 확인하고 불일치·용량 초과는 누락 사유로 남긴다. 자료 부족을 P1의 구현 부재로 자동 판정하지 않으며 큰 파일의 자동 발췌·추가 호출은 하지 않는다.

동일 파일은 경로 표기가 아닌 실제 경로로 묶는다. 충돌 검증 후 정상 파일에만 고정 순서로 용량을 배분한다. 최종 실행 기록이 없어도 Agent 3 시험의 stdout/stderr를 연결하며, 자체 로그 해시와 존재하는 manifest의 시험/로그 해시를 확인한다. 중간·최종 기록은 출처별로 보존하고 합격으로 승격하지 않는다. P1 실행 완료와 P2 평가 준비 중단은 대시보드에서 별도로 안내한다. 지원 근거·전체 입력 상한과 제외 범위는 유지하므로 자료 수집을 모델 평가 완료나 원본 전체 전송으로 설명하지 않는다.

역할별 파일 선택은 `attempt`/`manifest`가 이름에 들어 있는지에만 의존하지 않는다. 최종 검토·선택/제외·중단/오류 기록을 해당 역할에 전달하고, 최상위/후보별 A3 자료를 함께 지원한다. 당시 승인 TC 스냅샷은 A2/A3에, 검토 입력의 `catalog`, `compiler_recovery_facts`, `execution_interface`, `compiler_plan_facts`는 해당 역할의 `retained_reference_context`에 원문으로 연결한다. 설명을 실행 성공 증거로 보지 않으며 경로 제외·중복 참조·전송 한도는 유지한다. 승인 스냅샷이 전체 기본 TC 목록을 대신한다고 추정하지 않는다. 실제 API 요청을 저장하지 않은 Run은 호출 원문 미확보로 표시하며 없는 요청이나 응답을 재구성하지 않는다.

모든 읽은 JSON은 역할 패킷의 `trace.evidence_delivery`에 전달 상태를 기록한다. 알 수 없는 파일은 임의로 모델에 보내지 않고 로컬 보존/비선택으로 표시하므로 새 산출물 형식 도입 시 이 목록을 대조해야 한다. 2,000,000바이트 이상 JSON·링크·다른 실행 번호·요청 불일치는 수집 오류이며 조용히 미실행으로 처리하지 않는다. 사람 검토 문서는 같은 Run/최종 보고/실행/본문 해시를 확인한 안내 자료이고 공식 승인 완료 증거가 아니다. 실제 승인 이력 전체의 자동 의미 평가는 기존 범위 밖이다.

수집 시 요청·SRS의 저장 파일명을 고정 경로와 대조하고, Run manifest에 원본 해시가 있으면 일치 여부를 검사한다. 해시 없는 과거 입력은 `UNVERIFIED_NO_SAVED_HASH`, 저장 요청 없는 경우는 `UNAVAILABLE_NOT_SAVED`로 표시하며 원본 검증 완료로 취급하지 않는다. 기록된 해시/파일 참조가 틀리면 현재 자산으로 대체하지 않고 준비 오류로 중단한다. 알림 전달 목록은 폴더 내 파일 존재가 아닌 검증된 연결과 실제 입력 포함 여부를 따른다.

**현재 목표·실행 순서·반복 정책은 이 문서를 기준으로 합니다.** 이전의 ‘Agent 2 단독 최초 생성 5회 우선’ 계획을 대체합니다. 단독 평가는 원인 분석용이며 전체 흐름 평가의 선행 필수 단계가 아닙니다. 이 변경은 문서 계획의 정정이며 실제 반복 실행기 구현 완료를 뜻하지 않습니다.

## 1. 목적과 평가 대상

프로젝트 1의 **Agent 1 → Agent 2 → Agent 3 → Agent 4 전체 흐름**을 같은 조건에서 반복하고, 매 회차 네 역할의 결과·Checkpoint 판정·단계 간 연결을 각각 평가합니다. 최종 보고서만 평가하거나 TC 품질만으로 전체 품질을 대표하지 않습니다.

이 문서의 프로젝트 1은 실제 모델 기반 `qa-agent-pipeline-v2`입니다. `portfolio_export`의 V1은 Fixture 기반 Workflow Prototype이며 과거 비교·평가기 자체 시험용입니다. V1 계약을 V2에 그대로 강요하지 않습니다.

프로젝트 1은 QA를 수행합니다. 프로젝트 2는 실행을 관리하고 보존된 입력·산출물·증거로 그 수행을 평가하는 것이 목표입니다. 제품 시험 통과, Agent의 올바른 업무 수행, 평가 자료의 충분성, 사람의 공식 자산 승인은 서로 다른 판단입니다.

## 2. 주 시험과 보조 시험

| 구분 | 실행 범위와 입력 | 목적 |
|---|---|---|
| **주 시험 · 전체 흐름 반복** | 같은 변경 요청·SRS·공식 TC·제품 시작 상태에서 Agent 1부터 새로 실행. 후속 Agent에는 해당 회차 앞 단계의 실제 결과 전달 | 요구사항 해석부터 실행·보고까지의 품질, 오류 전파와 차단, 반복 일관성 |
| 보조 · Agent 단독 시험 | 검토된 동일 단계 입력으로 문제 역할만 실행 | 분석 오류인지 TC 설계 오류인지 등 원인 구분. 전체 결과와 별도 집계 |
| 보조 · 저장 기록 검사 | 과거 산출물 읽기 전용 검사 | 평가기 연결·역사적 공백 확인. 새 실행이나 반복 Trial로 세지 않음 |
| 보조 · 평가기 자체 시험 | 정상·오류 합성 자료 및 모의 응답 | 누락·오탐·미탐·호출 한도·집계 검사. 실제 Agent 품질로 세지 않음 |

전체 흐름에서는 Agent 1의 분석을 고정 정답으로 교체하지 않습니다. Agent 2 이후 입력이 회차마다 달라지는 것은 전체 흐름에서 관찰할 현상입니다. 이 변동을 해당 Agent 자체의 변동이라고 단정하지 않고 필요할 때 단독 시험으로 분리합니다.

## 3. 한 회차의 순서 · 목표 연결

초기 연결은 **순차 실행**으로 계획합니다. 프로젝트 2가 준비·호출을 관리하되, 프로젝트 1 한 회차가 정상 종료 또는 차단·오류로 끝난 뒤 확보된 자료를 평가합니다. 다음 회차는 상태를 다시 준비한 뒤 시작합니다. 단계별 자료는 생성 시점에 보존하고, 평가자가 실행 중 산출물을 수정하지 않습니다.

```text
프로젝트 2: 기준·호출 예산·독립 실행 위치·제품 시작 상태 준비
  ↓
프로젝트 1: Agent 1 분석 → CP1 → Agent 2 TC 설계 → CP2
          → Agent 3 계획·CP3 검사·코드·후보 시험
          → 관련 기존 TC 실행 → Agent 4 분류·보고·CP4
  ↓ 정상 종료 또는 차단·오류 시점까지의 자료 보존
프로젝트 2: A1 평가 / A2 평가 / A3 평가 / A4 평가
          + Checkpoint 차단·과잉 차단 / 단계 연결 평가
  ↓
원본·평가 결과 저장 → 다음 회차 준비 → 예정 5회 집계 → 사람 검토
```

이는 정상 후보가 있는 대표 경로이며 모든 요청에서 모든 하위 작업을 강제로 실행한다는 뜻은 아닙니다. 실제 제품 진입점은 `pipeline`(A1~3·후보 시험), `execute`(후보 결과 확인·관련 기존 TC 실행), `agent4`(분류·보고)로 나뉩니다. 프로젝트 2의 `full-flow`는 이 경계를 유지해 호출하며 무과금 연결을 검증했습니다. 실제 모델 성공 경로는 승인 후 확인합니다.

프로젝트 1의 Checkpoint만 기존 계약에 따라 후속 진행과 제한 재작성을 제어합니다. 프로젝트 2의 평가 의견이나 정답 힌트는 해당 회차 또는 다음 회차의 생성 입력으로 되돌려 보내지 않습니다. 평가기는 품질 판정을 위한 관찰자이며 기존 Checkpoint를 대체하지 않습니다. 예산 초과·안전 문제는 평가 운영 측에서 중단할 수 있고 사유를 별도 기록합니다.

### 정상 경로가 아닌 경우

- **CP1/CP2 차단:** 확보된 초안·검사·수정 기록은 평가합니다. 계약상 실행되지 않은 후속 Agent는 미실행으로 남기고 PASS나 해당 없음으로 바꾸지 않습니다.
- **부분 진행:** 확정된 범위만 후속 실행하고 미정·제외 조건·질문이 보고까지 유지되는지 검사합니다. 요청하지 않은 알림을 새 필수 조건으로 만들지 않습니다.
- **기존 TC만 재사용:** 신규 계획·컴파일·후보 시험은 근거 있는 해당 없음이 될 수 있습니다. 선택된 기존 TC의 실제 실행과 Agent 4 보고는 여전히 평가합니다. 신규 TC를 억지로 만들지 않습니다.
- **후보 여러 개:** 한 후보만 대표로 고르지 않고 해당 회차 후보별 계획·검사·시험·제외 상태를 모두 보존합니다. 후보 수에 따라 호출 예산도 달라집니다.
- **Agent 4까지 도달하지 못함:** 프로젝트 2가 중단 요약을 만들 수 있으나 이를 Agent 4가 생성한 보고서라고 표시하지 않습니다.
- **기대되는 차단:** 잘못된 입력을 올바르게 차단했다면 차단 기준은 충족할 수 있습니다. 후속 단계 미실행 자체를 Agent 오답으로 세지 않습니다.

## 4. 네 역할의 수집 자료와 독립 평가

아래는 전체 반복 연결기에 필요한 수집 계약입니다. 현재 자동 수집이 모두 구현됐다는 표가 아닙니다.

| 대상 | 반드시 보존할 자료 | 평가할 내용 |
|---|---|---|
| Agent 1 | 실제 요청·SRS 입력, 분석 초안/수정본, 근거·미정 조건·질문·범위, 호출 및 CP1 기록 | 수치·조건·방향 보존, 필요한 질문, 영향 누락/과잉 확대, 근거 의미 |
| Agent 2 | 이번 회차 분석과 기존 TC 입력, 선택/제외 이유, 신규 TC 초안/수정본, CP2 기록 | 재사용 충분성, 요청 범위, 사용자 TC 기준의 준비·순서·시점·관찰값·근거·복원 |
| Agent 3 | 전달받은 TC, 당시 UI inventory, 후보별 계획/수정 이력·CP3, 코드 식별 정보, 후보 시험 및 기존 TC 실행 행·로그·복원 증거. 코드 본문과 화면/Trace 원본은 기본 AI 입력에서 제외 | AI: TC→계획의 의미·화면 연결·실행 주장. 프로그램: 계획과 관찰 기록 대조. 로컬 회귀: 코드 생성기 구현. 지원 불가/실패는 보존 |
| Agent 4 | 중립 실행 행·증거·미정 조건·질문 입력, 분석·최종 보고·CP4·외부 보고 미리보기 | 수치·상태 집계, 증거 기반 분류, TC/실행/증거 연결, 불확실성과 다음 행동·승인 경계 |
| Checkpoint | 검사 전 산출물, 규칙·판정·이유, 재작성 전후, 실제 인계 여부 | 독립 기준상 잘못된 결과를 차단했는지, 정상 결과를 과하게 막았는지 |
| 전체 연결 | 회차·단계·TC·원본 요구사항 연결, 인계 해시, 실행/제외/차단 범위, 공식 자산 전후 상태 | 누락·바꿔치기·오류 전파, 전체 완료 범위, 질문/실패 전달, 승인 전 자산 보호 |

[23개 상위 역할 명세](08_AGENT_EVALUATION_SPEC.md)와 [26개 세부 기준](12_DETAILED_RUBRIC.md)을 적용합니다. 현재 단일 역할 Judge 입력은 공통 2개를 포함해 A1 6개·A2 10개·A3 5개·A4 4개입니다. 공통 항목이 역할마다 반복되므로 이 숫자를 단순 합산해 고유 기준 수로 부르지 않습니다. E01~E04 및 전체 연결 평가의 자동 통합은 별도 구현이 필요합니다.

현재 controller-map-1.0 TC는 Agent 2의 실행 정의를 연결표로 화면 위치에 연결하고 허용 목록 컴파일러가 코드를 생성한 뒤 시험합니다. 위치 생성용 모델 호출은 없으며 별도 의미 검토는 유지합니다. 과거 TC의 모델 계획 경로는 당시 계약으로 구분합니다. 실행 정의·화면 연결·컴파일러·시험 환경의 문제를 나눠 보고 UI inventory 조회만으로 제품 동작을 검증했다고 하지 않습니다.

Agent 4는 **규칙 기반 분석기**입니다. 생성 모델 호출 대상은 아니지만 매 회차 결과를 평가해야 합니다. 평가 AI가 A4 보고서를 검토하는 호출은 별도의 평가 비용입니다. 분류 정답은 A4가 붙인 라벨에서 복사하지 않고 원본 관찰과 사람 검토로 정합니다.

## 5. 전체 흐름 5회 실행 계약

한 시나리오마다 전체 흐름 **5회 시도**를 계획합니다. 5회는 초기 변동 탐색이며 일반 성공률의 통계적 보장이 아닙니다. 첫 실제 연결 검증 1회는 수집·안전·평가 경로를 확인하는 리허설로 분리합니다. 리허설 후 코드나 기준을 바꿨다면 그 결과를 수정 후 5회에 섞지 않습니다.

1. 대상 commit·프롬프트·모델 설정·SRS·기존 TC·제품/하네스·입력·정답·평가기 버전과 해시를 고정합니다.
2. 매 회차 독립 작업 위치와 동일 제품 시작 상태를 준비합니다. 앞 회차의 생성 TC를 공식 자산으로 등록하거나 다음 회차 입력으로 누적하지 않습니다.
3. 프로젝트 1의 **기존 제한 재작성 정책을 유지하고 고정**합니다. 최초 초안·각 수정본·CP 결과를 구분해 보존하고 추가 호출도 계측합니다. 프로젝트 2 평가에 맞추기 위한 추가 재작성은 하지 않습니다.
4. 최초 생성만의 품질이 필요하면 재작성 비활성의 단독 시험을 따로 설계합니다. 전체 흐름 시험에서 임의로 기존 복구 정책을 끄고 같은 시험이라고 부르지 않습니다.
5. 한 회차의 실행 시작·완료/차단/오류, 각 단계 시도, 생성 및 평가 API 전송 시도·응답 확인·오류·사용량을 따로 기록합니다. 전체 회차 수와 API 수는 다릅니다.
6. 타임아웃은 서버 처리 여부가 불명일 수 있으므로 응답 성공으로 세지 않습니다. 중복 응답 ID·과거 Run 재조회도 새로운 생성으로 세지 않습니다.
7. 생성·평가·SDK 재시도의 상한을 Preview에 각각 제시하고 승인 범위에서만 실행합니다. 숨은 자동 재시도나 성공 5건을 채우기 위한 추가 회차를 허용하지 않습니다.
8. 예정 5회 중 중단·미실행도 전체 목록에 남깁니다. 준비·복원 실패나 예산 부족으로 후속 회차를 시작하지 못하면 그 사유를 보존합니다.
9. 반복 묶음 도중 코드·정답·프롬프트를 변경하지 않습니다. 수정이 필요하면 묶음을 종료하고 별도 버전의 비교 시험으로 진행합니다.

### 호출 예산

전체 흐름 5회는 API 5회도, 항상 생성 5회+평가 5회도 아닙니다.

- P1 호출: A1 분석 + A2 설계 + 각 단계의 의미 검토 + 허용된 재작성. 과거 TC의 A3 위치 생성 호출이 있으면 함께 합산합니다. 현재 연결표 조립은 API가 아닙니다. 기존 `generation` 예산 필드에 모든 P1 호출을 합산하며 SDK 자동 재시도는 0회입니다.
- 로컬: 코드 컴파일·제품 시험·기존 TC 실행·A4 분류·코드 검사. 모델 API 호출과 구분합니다.
- 평가: 실제 평가 가능한 역할별 패킷 호출 + 향후 전체 연결 평가에 선택한 방식. 자료 없는 역할을 호출해 결과를 꾸미지 않습니다.

현재 연결표 TC 후보 1개, A1/A2 생성 각 1회, A1~A3 의미 검토 각 1회, 재작성 0회, A1~A4 별도 평가 각 1회를 가정하면 회차당 P1 5회·평가 4회입니다. 5회차는 P1 25회와 평가 20회로 **총 45회**입니다. 이는 설명용 가정이며 승인 한도나 실행 결과가 아닙니다. 과거 A3 위치 생성 경로라면 해당 호출을 추가합니다. 후보 수·재작성·미실행 분기에 따라 실제 호출 수가 달라지므로 기존 상한에서 중단합니다.

## 6. 결과 기록과 해석

한 회차에 A1·A2·A3·A4의 결과 영역 4개와 Checkpoint·연결 평가를 남깁니다. 모든 영역을 채운다는 것은 모두 PASS를 발급한다는 뜻이 아닙니다. 다음 개념은 **목표 기록 설계**이며 현재 모든 CLI가 같은 상태 Enum을 구현한 것은 아닙니다.

| 구분 | 기록 원칙 |
|---|---|
| 실행 여부 | 완료·차단·오류·미실행과 이유. 실제 실행과 계획된 실행을 구분 |
| 항목 판정 | 근거 있는 충족/위반, 판단 보류, 사전 적용 조건에 따른 해당 없음 |
| 증거 부족 | 미평가/검토 필요 또는 평가 오류. 무조건 Agent 오답으로 변환하지 않음 |
| 원인 | AGENT/HARNESS/DATASET/EVALUATOR/ENVIRONMENT 후보와 근거. 책임 미확정 보존 |
| 전체 완료 | 요청 전체·확정 부분·차단 범위를 구분. 제품 실행 PASS를 요청 전체 완료로 치환하지 않음 |

**제품 시험 FAIL ≠ Agent 평가 FAIL.** 기대값과 다른 동작을 A3이 정확히 발견하고 A4가 불일치 후보로 보고했다면 해당 평가 항목은 충족할 수 있습니다. 반대로 제품 시험이 PASS여도 TC가 필요한 검증을 빠뜨렸다면 Agent 품질에는 문제가 있습니다.

상위 분석이 잘못된 경우 하위 Agent가 받은 입력을 충실히 처리했는지와 원래 요청 전체가 충족됐는지를 분리합니다. 잘못된 최종 결과를 하위 Agent 하나의 책임으로 단정하지도, 상위 오류를 그대로 따른 것만으로 전체 흐름을 통과시키지도 않습니다.

### 집계

- **전체 기준 충족 회차 / 예정 5회:** 오류·미실행·평가 보류는 충족 분자에 넣지 않고 사유별 건수를 함께 표시합니다. 충족하지 못한 모든 회차를 Agent 오답이라고 부르지 않습니다.
- **Agent별 도달·평가 가능 횟수:** 예를 들어 A3가 3회만 실행됐다면 3회 평가 결과와 미실행 2회의 이유를 같이 표시합니다. 부분 자료 평가도 구분합니다.
- **핵심 일관성:** 같은 관점으로 비교 가능한 결과 수를 분모와 함께 제시합니다. 표현·임의 TC ID의 차이만으로 실패시키지 않습니다. 동일 오답 반복과 정답 충족은 별도입니다.
- **최초/수정 후 결과:** 한 Trial 안의 시도로 구분합니다. 수정 후 성공으로 최초 오류를 지우지 않습니다.
- **Checkpoint 정확성:** 잘못된 산출물 차단과 정상 산출물 과잉 차단을 각각 독립 정답과 대조합니다. CP PASS를 정답으로 재사용하지 않습니다.

5회가 모두 기준 18도를 16도로 바꿨다면 일관성은 높아도 전부 기준 위반입니다. 기존 합성 경로의 95%·90% Gate나 초기 평균 4점 제안은 현재 전체 흐름의 합격 기준으로 승계하지 않습니다. 코드 검사·의미 검토·사람 교정 범위를 표시하고 근거 없이 최종 품질 PASS를 내지 않습니다.

## 8. OpenAI 평가자 연결

현재 단일 역할 호출 경로는 `openai_judge.py`의 `JudgePacket`을 사용합니다. `agent_id`는 A1/A2/A3/A4와 별도 E2E를 지원합니다. full-flow-0.6는 E2E 모델을 자동 호출하지 않으며 A4-01/03을 파이썬 채점으로 분리해 A4 모델에는 공통 2개와 A4-02/04만 전달합니다. 제품·환경·고정 사례 집계와 요구사항·출처까지 대조하며 질문/정보 부족 보존 검사는 저장 경로와 공유합니다. E04는 승인 전후 증거 없이 통과로 채점하지 않습니다. 점수는 score-0-5-v2이며 예전 점수와 자동 혼합 비교하지 않습니다. 같은 제공자를 쓰는 것만으로 평가 정확성이 확보되지는 않습니다.

`sources`에는 사람이 선정한 필요한 요청·산출물·근거를 넣습니다. 전체 Run/HTML/환경변수 자동 수집은 하지 않습니다. [자료 키·26개 기준·Preview 해석](12_DETAILED_RUBRIC.md)을 확인하세요.

1. `python -m eval_harness judge-openai --packet PACKET.json --model MODEL_ID --role-rubric`으로 전송 내용·출력 계약·1회 호출 한도·확인용 해시를 봅니다. 키나 외부 호출은 필요 없습니다.
2. 사용자가 실제 전송·모델·비용을 승인한 뒤 같은 명령에 `--execute --approval-sha256 PREVIEW_HASH`를 붙입니다. 해시는 입력 변경 방지 수단이지 사용자 승인 자체의 증명이 아닙니다.
3. `JUDGE-...`에 패킷·Preview·시작/종료·응답/요청 ID·사용량·항목 판정을 저장합니다. 현재 호출기는 고정 OpenAI origin, `store=False`, 자동 재시도 0, 120초 타임아웃, 출력 최대 6,000토큰입니다.
4. 누락·중복 항목, 확인되지 않는 인용, 필수 증거가 없는데 PASS/해당 없음으로 처리한 응답은 출력 계약 오류입니다. 코드 FAIL은 AI PASS로 덮지 않습니다. 인용 존재가 판단의 정확성을 보장하지는 않습니다.

평가 본문의 자체 크기 한도는 UTF-8 JSON 250,000바이트입니다. `payload_bytes`와 `payload_limit_bytes`는 근거 번호·평가 기준을 포함한 사용자 메시지 본문을, `request_bytes`는 시스템 지침을 포함한 요청 JSON(출력 스키마 제외)을 나타냅니다. 실제 API의 모델 입력 한도는 토큰 기준으로 별도 적용되며 이 바이트 검사가 호출 성공이나 비용을 보장하지 않습니다. 한도 초과 시 자료를 몰래 줄이거나 모델 호출을 추가하지 않습니다. 호출 횟수·출력 6,000토큰·자동 재시도 0과 응답 진단 사본 120,000바이트 제한은 변경하지 않았습니다.

`openai-judge-1.4`부터 전송 시 자료 말단 값을 `[근거 번호, 원래 값]`으로 표시하고 모델은 `evidence_ids`와 입력 패킷 해시를 반환합니다. 번호는 원문 위치를 프로그램이 연결하기 위한 식별자이며 점수·합격 라벨이 아닙니다. 매핑은 `evidence_catalog.json`, 모델 응답은 `received_response.json`, 원문으로 연결한 판정은 `result.json`에 분리 보존합니다. 보고서의 기존 `source_id/path/quote` 형식은 유지합니다. 없는 번호·중복 번호·다른 패킷 응답은 거절하고 의미가 무관한 근거를 자동으로 올바른 근거로 바꾸지 않습니다. 긴 문자열은 전체 값 단위이며, 번호 일치만으로 의미 관련성을 검증했다고 주장하지 않습니다. 원본·번호 표시 자료·새 출력 계약이 전송 승인 해시에 함께 연결되므로 이전 Preview 해시로 새 호출을 승인할 수 없습니다.

`full-flow`는 프로젝트 1 생성·근거 검토 SDK 시도·실제 HTTP 전송 시도·응답 ID를 기록하고 역할별 Judge를 순차 연결합니다. SDK 자동 재시도는 0으로 고정하고 기존 CP 재작성은 유지합니다. 이전 P1 버전의 기존 TC 재사용 경로는 A4까지 완료했지만 별도 Judge는 오류로 중단됐습니다. 최신 P1의 전체 Live 재검증·의미 평가 완료와 구분합니다. Agent 2 예시 패킷은 역할 호출 사용 예일 뿐 주 시험의 범위가 아닙니다.

## 9. 안전 경계와 문서 우선순위

원본 프로젝트 1 코드·SRS·공식 TC·포트폴리오는 읽기 전용으로 유지합니다. 실제 시험은 버전이 고정된 별도 작업 위치에서 수행하도록 설계하며, 임시 작업 위치는 컨테이너나 OS 권한 격리를 제공하는 보안 Sandbox가 아닙니다. 시작 상태 준비·복원·원본 보호 실패는 기록하고 안전한 후속 실행을 보류합니다.

외부 게시·사람 승인·공식 등록은 반복 평가의 부수효과로 실행하지 않습니다. 승인 전 자산이 유지되는지는 확인하되 실제 승인 후 등록 경로 시험은 별도 권한과 자료가 필요합니다. 미실행 범위를 승인 완료로 표시하지 않습니다.

- 현재 목표·순서·반복 정책: **이 문서**
- 역할/증거/판정 설명: [계약](01_AGENT_CONTRACTS.md), [평가 명세](02_EVALUATION_SPEC.md), [역할 명세](08_AGENT_EVALUATION_SPEC.md), [세부 기준](12_DETAILED_RUBRIC.md)
- 구현 경로와 한계: [구현 매핑](05_IMPLEMENTATION_MAPPING.md), [README](../README.md)
- 최신 검증·과거 시행착오: [인계 문서](../PROJECT_HANDOFF.md)
- V1 Fixture·초기 저장 검사·과거 Run 리뷰는 기록으로 보존하며 현재 계획보다 우선하지 않습니다.

교육자료와 평가 가이드에서 참고한 기준·사람 교정 원칙의 출처는 [세부 평가 기준](12_DETAILED_RUBRIC.md#1-교육자료에서-가져온-내용)에 정리했습니다.

## 10. 전체 실행 연결기 사용법

`full-flow`는 프로젝트 1의 `pipeline → execute → agent4(send=False)` 경계를 호출합니다. A1~3 모델 요청은 별도 계수기를 거치고 A4는 기존 규칙 분석기를 사용합니다. 회차마다 새 사본을 만들며 원본 코드·SRS·공식 자산 해시와 자산 목록을 전후 대조합니다. 연결기 구현과 모의 분기 검증을 실제 모델 실행 성공으로 해석하지 않습니다.

1. `benchmarks/v2/full_flow.example.json`의 요청·독립 정답 파일·모델·1회/5회·후보 수·생성/평가 상한을 검토합니다. 독립 정답 초안은 `DRAFT`이며 사람 정답으로 확정하지 않았습니다.
2. README의 Preview 명령으로 원본 커밋·입력/평가기 해시·전송 범위·최대 호출 수를 확인합니다. 실제 호출은 사용자 승인 후 같은 Preview 해시로 실행합니다. 중간에 입력·코드가 달라지면 다시 Preview가 필요합니다.
3. 예시 1회는 P1 생성·재작성·근거 검토 합산 최대 10회와 Judge 최대 4회, 합계 최대 14회입니다. P1 응답 출력 한도는 요청당 12,000토큰, Judge는 6,000토큰입니다. SDK 자동 재시도 0은 프로젝트 1의 CP 재작성을 끈다는 뜻이 아닙니다. CP 재작성과 근거 검토 모두 기존 생성 예산에서 차감합니다.
4. Agent별 실제 요청 시도·HTTP 전송 시도·응답 ID·응답 수신을 구분합니다. 타임아웃 후 서버 완료 여부는 알 수 없으며 비용 0으로 단정하지 않습니다. 응답 중복·연결 오류·한도 초과·원본/사본 변경 시 남은 회차는 미실행으로 보존합니다. 성공 5회가 될 때까지 추가 호출하지 않습니다.
5. 한 회차 자료로 A1/A2/A3/A4를 각각 평가한 뒤 다음 회차를 진행합니다. 재사용 전용이면 A3의 신규 계획은 해당 없지만 기존 TC 실행은 확인합니다. 여러 후보와 제외·미실행도 보존합니다. 평가 의견과 독립 정답은 생성 Agent에게 돌려보내지 않습니다.
6. `FLOW-.../result.json`, `trial-N/record.json`, `comparison.json`, 역할별 패킷/Preview/Judge 결과, `evidence.zip`을 보존합니다. ZIP에는 회차 사본의 원본 자료를 바이트 그대로 보존하며 기존 인계 해시를 다시 쓰지 않습니다.
7. 역할 패킷에서 실제 요청의 JSON 문자열을 구조화하고 중복 값은 최초 자료 위치를 참조합니다. 원문 해시·원본 요청 파일은 남깁니다. 작업 위치 표기만 명시적으로 대체하고, 미처리 절대경로·비밀정보·전체 HTML이나 용량 초과는 전송 전에 차단합니다. 임의 문장 축약으로 중요한 증거를 버리지 않습니다.
   `full-flow-0.3`에서 도입한 정책은 생성 요청의 지침·입력은 유지하고 `purpose=grounding` 요청 본문과 중복된 검토 입력 본문을 제외하는 것입니다. 현재 0.11은 저장 검토 입력의 `context.catalog`와 `context.compiler_recovery_facts`만 원문으로 남기고 나머지 본문은 계속 제외합니다. 각 원본 파일 해시와 명시적 제외 표시, 역할별 호출 기록·검토 결과·Checkpoint·재작성 기록은 남깁니다. 원본 바이트는 로컬 압축 증거로 보존합니다. 해시만으로 제외된 본문의 의미나 지침 준수까지 평가할 수는 없습니다. 이 정리 뒤에도 한도를 넘으면 기존대로 전송 전에 중단합니다.
8. 재작성 중 중단되어 최종본이 없더라도 저장된 A1~3 초안을 `DRAFT_ONLY_NO_FINAL_HANDOFF`로 수집합니다. 최종본·검사 통과·후속 인계 완료로 바꾸지 않습니다. 원본 기록은 그대로 두고, 보완 후 오프라인 재수집은 `post-review/`에 별도 기록합니다.

### 결과 해석과 남은 검증

- `COMPLETED`는 회차 수집 처리가 끝났다는 상태입니다. Agent/제품 전체 통과가 아닙니다. 중간 CP 차단도 완료된 관찰 기록이 될 수 있습니다.
- 역할별 구조·텍스트 지문은 ID 등 일부 가변 메타데이터를 제외한 값의 차이를 찾습니다. 표현이 달라도 같은 의미인지, 5회 모두 같은 오답인지까지 판단하지 않습니다. 독립 정답·사람 교정이 필요합니다.
- 전체 연결 코드 검사는 실행 행/집계·해시 연결·일부 정보 부족/질문 보존·자산 보호에 한정됩니다. 조건별 실제 검증의 의미 충분성, 실패 원인의 정답 분류, Checkpoint 과잉 차단/미탐의 전면 평가와 Live 5회 결과는 아직 없습니다.
- 예시 요청은 현재 공식 TC로 재사용될 수 있습니다. 신규 계획 생성을 억지로 유도하지 않습니다. 이 리허설에서 A3 신규 계획이 해당 없다면 그 경로의 실제 모델 검증에는 별도 사례·예산이 필요합니다.
- Notion/Slack 게시·사람 승인·SRS/공식 TC 등록은 수행하지 않습니다. 생성·Judge는 OpenAI를 쓰지만 서로 별도 요청이며, 동일 제공자 평가만으로 독립 정확성을 입증하지 않습니다.
