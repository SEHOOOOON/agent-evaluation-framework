# Agent 평가 계약서

문서 ID: `CONTRACT-001` · 문서 버전: `v0.4`

현재 대상은 프로젝트 1 V2(`qa-agent-pipeline-v2`)입니다. [전체 흐름 실행 계획](11_RELIABILITY_EVALUATION_PLAN.md)을 따릅니다. 이 문서의 **전체 회차·수집·평가 연결 계약은 구현 목표**이며 기존 코드의 모든 필드·Enum이 이미 이를 지원한다는 의미가 아닙니다.

## 1. 기준과 출처

- 제품 요구와 요청: 대상 Run의 요청·SRS·공식 TC 및 실제 전달 입력.
- 역할·검사 동작: 대상 버전의 `src/qa_pipeline_agent1.py`, `qa_pipeline_agent2.py`, `qa_pipeline_agent3.py`, `qa_pipeline_execution.py`, `qa_pipeline_reporting.py`, `qa_pipeline_orchestrator.py` 및 `docs/PROJECT_GUIDE.md`.
- 역할 평가: [23개 상위 항목](08_AGENT_EVALUATION_SPEC.md)과 [26개 세부 기준](12_DETAILED_RUBRIC.md).
- TC 상세도: [사용자가 제공한 기준](../benchmarks/v2/TC_REFERENCE.md).
- 독립 정답: 요청에서 도출한 포함/제외·기대값과 사람이 검토한 중립 실행 증거. 대상 Agent 결과나 CP PASS에서 정답을 복사하지 않음.

초기 V1의 Markdown/YAML 1대1 대응, `approved`·`excluded_assertions` 등 필드와 특정 수정 횟수를 V2에 그대로 적용하지 않습니다. `rules/project1_agent_rules.yaml`은 보존한 개발·합성 경로의 카탈로그이지 V2 계약의 대체물이 아닙니다.

## 2. 전체 회차 계약

한 시나리오의 같은 원본 요청·SRS·공식 TC·제품 시작 상태로 매번 Agent 1부터 시작합니다. Agent 2 이후에는 **그 회차의 실제 앞 단계 출력**을 전달합니다. 중간 결과를 사람이 만든 정답으로 교체하지 않습니다.

회차마다 다음을 보존하도록 연결합니다.

- 시나리오·회차·단계·후보/TC ID, 프로젝트 1 Run ID와 평가 ID의 대응.
- 코드·프롬프트·모델 설정·입력·제품/하네스·기준 버전과 해시.
- 실제 단계 입력, 최초 출력, CP 결과, 각 수정 시도와 최종 출력.
- 호출 시도·응답 확인·오류·시간·사용량, 제품 시험 결과·증거.
- 완료/차단/오류/미실행 이유, 해당 없음의 적용 근거.
- A1~4 각각의 평가와 Checkpoint·연결 평가. 없는 산출물을 만들어 채우지 않음.

후속 인계를 막는 것은 프로젝트 1의 기존 Checkpoint 계약입니다. 프로젝트 2의 평가 결과는 생성 입력에 되돌려 보내지 않습니다. 운영 예산·안전 중단은 별도 사유로 기록합니다.

## 3. Agent 1 · 요구사항 분석

입력은 요청·관련 SRS·대상 버전의 역할 계약입니다. 산출물은 변경/유지 조건·인용·영향 범위·정보 부족·확인 질문·진행 판단입니다.

확인할 사항:

- 수치·대상·상태 방향을 바꾸지 않는지.
- 요청하지 않은 알림·색상을 새 필수 정보로 요구하지 않는지.
- 핵심 정보가 없으면 질문하고, 안전하게 분리 가능한 확정 범위는 부분 진행하는지.
- 근거가 실제 주장과 연결되는지. 인용의 존재만으로 의미를 통과시키지 않는지.

## 4. Agent 2 · TC 대조와 설계

입력은 해당 회차 A1 분석·관련 SRS·기존 TC·QA 기준입니다. 신규 TC뿐 아니라 재사용 선택·제외 이유·미정 범위·SRS 개정 제안도 보존합니다.

확인할 사항:

- 이름이 아니라 실제 검증 범위와 기대값으로 기존 TC를 선택하는지.
- 충분한 기존 TC가 있으면 불필요한 신규 TC를 만들지 않는지.
- 사용자 기준 TC-R01~07: 준비·대상, 조작 순서, 판정 시점, 관찰 위치/값, 필요한 범위, 근거, 복원 성공 확인.
- 상세함을 위해 없는 요구사항·기대결과를 추가하지 않는지.
- 기존 정책 안의 시험에 불필요한 SRS 개정을 제안하지 않는지. 개정이 필요하면 전체 인수기준 셀에서 미변경 조건도 보존하는지(TC-R06).
- 초안·CP2 통과와 사람의 공식 등록 승인을 구분하는지.

A1 입력이 잘못된 경우 원래 요청 위반과 A2 자체의 전달 입력 처리 오류를 분리해 기록합니다. 회차별 A1 변동을 A2 단독 변동이라고 단정하지 않습니다.

## 5. Agent 3 · 계획·컴파일·실제 시험

현재 controller-map-1.0 TC의 Agent 3은 **A2 실행 정의의 화면 연결 → 결정론적 코드 생성 → 실제 시험**으로 평가합니다. 위치 생성용 모델 호출은 없으며 별도 의미 검토는 유지합니다. 과거 TC의 모델 계획 경로는 당시 계약으로 구분합니다.

- 전달된 TC·UI inventory와 후보별 최초/수정 계획, CP3 기록을 보존.
- TC의 대상·조작·기대값·확인 시점·복원이 계획에서 유지되는지 확인.
- 허용 목록 컴파일러가 계획을 코드로 정확히 옮겼는지 확인.
- 실제 후보 시험·관련 기존 TC 실행의 상태·관찰·화면/로그/Trace·복원 증거 확인.
- 여러 후보의 제외·실패·미실행을 하나의 성공 후보로 대표하지 않음.
- 기존 TC 재사용만 있으면 새 계획/컴파일은 해당 없음이 가능하나 실제 회귀 실행 증거는 필요.
- 실행 정의·화면 연결 오류, 컴파일러 오류, 제품 불일치, 환경/하네스 오류를 구분하며 책임 미확정을 허용. 과거 경로에서는 모델 계획 오류도 구분.

UI 요소 조회는 제품 시험 성공이 아닙니다. 코드 구문 통과·해시 일치도 실제 실행을 대체하지 않습니다. 기대값 변경이나 assertion 삭제로 실패를 성공으로 만들면 안 됩니다.

## 6. Agent 4 · 규칙 기반 분석과 보고

Agent 4 자체는 생성 모델을 호출하지 않습니다. **매 회차 원본 실행 행과 A4 분석·보고·CP4 결과를 각각 대조**합니다.

- TC별 원본 상태와 전체/유형별 합계가 유지되는지.
- 중립 관찰·로그가 원인 분류를 뒷받침하는지.
- `PRODUCT_MISMATCH_CANDIDATE`를 제품 결함 확정으로 과장하지 않는지.
- 같은 TC·Run의 증거를 연결했는지.
- 실패·미실행·미정 범위·사용자 질문·다음 행동이 최종 보고에 남는지.
- 자동 검사 통과와 사람의 SRS/공식 TC 승인을 구분하는지.

A4 라벨이 이미 포함된 V1 Fixture는 독립 원인 분류 정확도의 근거에서 제외합니다. V2의 중립 입력과 사람 정답 준비 여부는 별도로 확인합니다. 동일 규칙·동일 증거로 실행하는 결정성 시험은 필요 시 보조로 수행합니다.

## 7. Checkpoint·단계 연결

CP1~CP4는 다음 단계 인계·실행/보고 허용 여부를 대상 코드 계약에 따라 제어합니다. 모든 CP가 동일한 수정 횟수나 복구 방법을 가진다고 가정하지 않습니다.

프로젝트 2는 각 CP의 검사 전 출력·판정·이유·수정 이력·실제 인계를 독립 기준과 비교합니다. 잘못된 결과를 통과시킨 경우와 정상 결과를 막은 경우를 따로 확인합니다. 초기 오류가 수정돼도 최초 위반 기록은 남깁니다.

조건→TC→계획/코드→시험→보고의 연결, 미정 조건·질문·제외 사유의 전달, 승인 전 자산 불변을 확인합니다. 중간에 차단됐다면 후속 Agent 미실행을 명시하고 프로젝트 2 중단 요약을 A4 산출물로 표시하지 않습니다.

## 8. 생성·평가 호출과 오류 계약

- 전체 흐름은 시나리오별 5회 시도. 기존 제한 재작성 정책을 고정하고 각 호출을 따로 기록.
- P1의 A1/A2 생성·각 단계 의미 검토·허용 재작성과 P2 평가 모델 호출 예산을 분리. 과거 A3 위치 생성 호출도 실제 호출 기록에 따라 집계하고 현재의 결정론적 연결과 A4 로컬 실행은 API로 세지 않음.
- 타임아웃·오류·미실행을 성공 5건을 채우는 추가 시도로 대체하지 않음.
- 실제 수집 가능한 요청/응답 ID·시각·사용량을 기록하고 없는 정보는 unknown으로 보존.
- 키·인증 헤더·불필요한 로컬 경로·전체 HTML을 평가 패킷에 넣지 않음.
- 준비/복원 실패, 비용 상한, 평가기 오류를 Agent 오답과 구분.

`JudgePacket` 자체는 단일 역할 1회 평가 계약입니다. `full_flow.py`가 실제 회차 자료를 역할별 패킷으로 구성하고 순차 평가합니다. `full-flow`의 무과금 검증과 실제 모델 평가 정확성은 구분하며 E2E 의미 충분성·Checkpoint 과잉 차단 교정은 남아 있습니다.

## 9. 사람 검토와 권한

사람은 독립 기준의 적절성 및 Judge 판정의 근거를 대조합니다. 충돌 시 Agent·하네스·데이터·평가기·환경의 원인을 조사하고 검토자·이유·증거를 별도로 보존합니다. 기준 변경은 새 버전이며 과거 판정을 조용히 덮어쓰지 않습니다.

평가용 사람 검토는 프로젝트 1의 공식 SRS·TC 등록 승인이 아닙니다. 반복 시험은 공식 자산과 원본을 보호하고 외부 게시·공식 등록을 수행하지 않습니다. 승인 후 등록 경로의 실제 시험은 별도 승인 범위입니다.
