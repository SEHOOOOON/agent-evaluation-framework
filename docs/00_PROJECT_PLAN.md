# 프로젝트 기획서

문서 ID: `PLAN-001` · 문서 버전: `v0.4`

## 1. 목적

**프로젝트 1의 Agent 1~4가 요구사항 분석부터 실제 시험·보고까지 정해진 기준으로 동작하는지 평가합니다.** 최종 산출물 하나가 아니라 역할별 결과·Checkpoint·단계 연결과 반복 일관성이 평가 대상입니다.

현재 대상은 실제 모델 기반 `qa-agent-pipeline-v2`입니다. 초기 `portfolio_export` V1은 Fixture 기반 Workflow Prototype으로 구분합니다. [현재 실행 계획 FLOW-v1.0](11_RELIABILITY_EVALUATION_PLAN.md)이 순서·횟수·중단·호출 예산의 기준이며 이 문서는 기획 요약입니다.

## 2. 핵심 질문

- Agent 1이 요구사항의 조건·수치·미정 범위를 정확히 분석했는가?
- Agent 2가 해당 회차 분석을 받아 필요한 기존 TC를 선택하고 상세 TC를 설계했는가?
- Agent 3의 계획·컴파일 코드·실제 시험이 TC의 대상·조작·기대값·시점을 보존하는가?
- Agent 4가 원본 결과·실패·미실행·질문을 근거에 맞게 분류하고 보고했는가?
- Checkpoint가 오류를 막고 정상 결과는 불필요하게 막지 않았는가?
- 같은 조건의 반복에서 범위·판단·관찰이 일관적인가? 같은 오답을 반복한 것은 아닌가?

## 3. 목표 구조

```text
프로젝트 2: 조건·버전·독립 시작 상태·예산 고정
→ 프로젝트 1 전체 실행: A1 → A2 → A3 및 관련 기존 TC 실행 → A4
→ 회차별 A1/A2/A3/A4 결과·Checkpoint·연결 평가
→ 원본과 평가 결과 보존
→ 예정 5회 비교·사람 검토
```

전체 실행·수집·역할 평가 연결기를 구현했고 무과금 분기를 확인했습니다. 실제 P1 모델 실행과 저장 결과에 대한 P2 역할 평가도 일부 수행했습니다. 다만 이 기록은 동일한 고정 조건의 반복 시험이 아니며, 사람 판단과의 대조·계획된 5회 비교는 남아 있습니다. 중간 차단·오류 시에도 해당 시점 자료와 후속 미실행을 남깁니다. 기존 TC만으로 충분한 경우 신규 계획·코드 생성을 강요하지 않습니다. 문제의 원인을 분리할 때만 해당 Agent의 고정 입력 단독 시험을 보조로 사용합니다.

## 4. 실제 구성요소와 평가

| 대상 | 프로젝트 1 V2 동작 | 프로젝트 2 평가 |
|---|---|---|
| Agent 1 | 모델 기반 구조화 분석 | 요구사항 충실성·근거·필요한 질문·범위 |
| Agent 2 | 모델 기반 기존 TC 대조·설계 | 재사용·검증 범위·사용자 TC 상세도·기대결과 |
| Agent 3 | A2 실행 정의의 화면 연결 + 허용 목록 컴파일러 + 후보 시험, 관련 기존 TC는 execute 경로. 과거 모델 계획은 당시 계약으로 구분 | TC→계획→코드·실행 의미 보존·복원·증거 |
| Agent 4 | 규칙 기반 분석·보고 | 집계·중립 증거 기반 분류·최종 범위와 질문 전달 |
| Checkpoint / 전체 연결 | 자동 검사·인계·제한 재작성 | 차단/과잉 차단·수정 전후·누락·오류 전파 |

Agent 4는 생성 모델이 아니며 Agent 3도 단순 기존 테스트 실행기가 아닙니다. 제품 시험 실패를 올바르게 검출·보고했다면 해당 Agent 평가 항목은 충족할 수 있습니다.

## 5. 현재 자산과 구현 범위

- `rules/project1_agent_rules.yaml`: V1에서 출발한 합성 행동 검사 카탈로그. V2 전체 의미 평가의 유일한 기준으로 사용하지 않음.
- `agent_rubric.py`: 저장 기록에 공통·역할·연결의 23개 상위 항목 표시.
- `detailed_rubric.py`: 26개 세부 조건·필수 증거·정상/실패 예시. 역할별 평가 패킷에 연결.
- Development YAML: 9개 설계 Case. 과거 3회/5회 설정은 해당 합성·개발 경로의 값이며 현재 전체 흐름 횟수 정책이 아님.
- 저장 Run 검사·모의 반복·별도 Judge 호출 경로: 구현. 일부 실제 실행·평가 기록은 [인계 문서](../PROJECT_HANDOFF.md)에서 확인할 수 있음. 사람 판단을 기준으로 한 평가자 교정·독립 Holdout 평가는 미완료.

개별 모듈과 명령은 [구현 매핑](05_IMPLEMENTATION_MAPPING.md), 실제 검증 수치는 [인계 문서](../PROJECT_HANDOFF.md)에 둡니다.

## 6. 실행·판정 원칙

전체 흐름을 주 시험으로 **시나리오별 5회 시도**합니다. 실제 연결 1회 리허설은 별도이며 변경된 버전의 결과를 한 묶음에 섞지 않습니다. 최초 초안과 프로젝트 1의 기존 제한 재작성 후 결과를 각각 보존합니다. 평가 의견을 다음 회차 생성에 주입하지 않습니다.

예정 횟수 대비 기준 충족·차단·오류·미실행, 역할별 도달/평가 가능 횟수, 핵심 값 일관성을 따로 보고합니다. 합성 경로의 95%/90% Gate를 전체 평가의 합격 기준으로 적용하지 않습니다. 중대한 위반을 평균 점수로 상쇄하지 않으며 의미 교정 전 최종 품질 PASS를 주장하지 않습니다.

## 7. 구현 순서

1. 전체 A1~4 실행·수집·시작 상태·예산 계약 연결
2. 무과금 모의 연결 및 정상/차단/재사용/다중 후보/오류 검증
3. 독립 정답 준비·승인 후 전체 경로 1회 리허설·평가자 교정
4. 고정 조건 전체 흐름 5회
5. 문제 역할 단독 재현·승인된 개선·새 버전 회귀 비교

## 8. 비목표와 보호

모델 학습, 모든 Agent의 범용 절대 점수, 자동 프롬프트 수정·배포는 범위 밖입니다. 원본 프로젝트 1·공식 SRS/TC·포트폴리오를 보호하고, 실제 실행은 고정 버전의 별도 작업 위치에서 준비합니다. 이는 OS 수준 보안 격리를 뜻하지 않습니다.

Notion/Slack 전송과 사람의 공식 등록 승인은 반복 평가에 포함하지 않습니다. 과거 Fixture·Run·검토 기록을 덮어쓰거나 다시 읽은 횟수를 새로운 Trial로 계산하지 않습니다.
