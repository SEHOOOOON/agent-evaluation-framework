1 개발 배경

변경 요청마다 반복되는 QA 업무에서 출발했습니다.

중앙제어 시스템을 검증하며 경험한 요구사항 대조·TC 검토·시험·보고를 개인 프로젝트로 연결했습니다.

실무에서는 요구사항이 바뀌면 기존 TC에서 영향받는 부분을 찾고, 필요한 시험을 추가한 뒤 결과와 수정 이력을 정리했습니다. 변경의 의미를 판단하는 일과 반복해서 조작하고 기록하는 일이 함께 있었습니다.

반복 작업을 AI와 자동화에 맡기고, 사람은 변경의 타당성과 결과 검토에 더 집중할 수 있을지 확인하고 싶었습니다. 실제 회사 자료 대신 가상 중앙제어 시스템과 예시 요구사항으로 분석부터 시험·보고까지 이어지는 흐름을 만들었습니다.

기획·검증 기준·시나리오 설계를 맡고, AI 코딩 도구를 활용해 구현과 검증을 진행한 개인 프로젝트입니다.

2 전체 흐름

분석 → 시험 설계 → 실행 → 보고 → 사람 판단

요청이 분석 결과 → 테스트케이스 → 실행 기록 → 보고서로 이어집니다. 각 단계는 앞에서 정한 기준을 전달받고, 마지막 등록은 사람이 결정합니다.

3 개발 과정에서의 고민

기준을 정해도 AI의 해석은 달랐습니다.

업무를 나누어 맡기는 것만으로는 단계마다 같은 판단을 유지하기 어려웠습니다.

처음에는 각 단계의 양식과 검토 기준을 자세히 정하면 결과도 일관될 것으로 기대했습니다. 하지만 같은 요구사항을 분석·설계·실행 단계에서 다르게 해석하는 경우가 있었고, 기준을 지나치게 세분화하면 정상적인 작성 차이도 막혔습니다.

그래서 이미 정한 원문과 시험 내용을 다음 단계가 다시 작성하는 부분을 줄였습니다. AI가 판단할 내용과 프로그램이 그대로 전달할 내용을 구분하고, 사람이 확인할 결과와 근거를 남기는 데 집중했습니다. 새로운 요청을 항상 처리하는 수준은 아니지만, 자동화를 설계할 때 어디에 판단을 맡겨야 하는지 배울 수 있었습니다.

5 Agent 2 · TC 설계와 품질 검토

기존 TC 검토와 변경분 테스트 설계

Agent 2는 확정된 조건과 기존 TC를 읽고 테스트를 설계합니다. 기존 TC로 충분한 부분과 새 시험이 필요한 부분을 나눕니다. 프로그램은 요청에 적힌 값과 TC의 준비·조작·검사·복원 절차를 대조합니다.

시험 범위 선정 정상·예외·경계값 등 시험 유형은 요청과 영향 범위에 맞춰 정합니다.

시험 전반

공통 QA 기준

요청한 변경에서 빠뜨리기 쉬운 조건을 확인합니다.

  • 정상·예외·경계값
  • 상태 변경과 회귀 영향

  • 모드별 제어 제한

  • 근거가 확인된 기대결과만 사용
  • 통과·실패 판단 기준
  • 기능에 맞는 검증 대상 선택
  • 자동화 가능 범위

선택한 TC의 공통 검토 항목

1. 요구사항에 근거가 있는가

요구사항의 출처·명시 코드·수치를 대조하고 근거 밖 값을 검사

2. 이 TC만으로 시험할 수 있는가

다른 TC에 의존하지 않는 준비·시험 절차. 상태 변경 시험은 복원도 확인

3. 무엇을 언제 확인하는가

어떤 조작 뒤 무엇을 관찰하는지 기대결과와 시점을 확인

4. 실제로 조작·확인할 수 있는가

검증 가능한 절차인지 검토하고 실제 요소·계획 검사는 Agent 3에서 수행

정상·예외·경계값을 모든 TC에 함께 넣지는 않습니다. 다만 선택한 TC의 근거·독립 실행 절차·기대결과·확인 시점은 공통으로 검토합니다. 상태를 바꾸는 시험은 준비 전 상태로의 복원과 확인도 필요합니다.

TC에서 보완 가능한 초안 오류가 발견되면, AI에 해당 TC와 검사 결과를 보내 최대 한 번 재작성하고 다시 확인합니다. 판단이 불확실하거나 검토 응답·호출에 오류가 나면 중단합니다. 통과한 TC만 Agent 3로 넘깁니다. 생성된 TC는 시험할 후보이며, SRS 변경안 반영과 공식 TC 등록은 사람 승인 후에 이루어집니다.

기존 TC가 있는데 왜 새로 만드나요?

기존 TC로 충분하면 새로 만들지 않습니다. 변경 요구사항을 기존 TC가 검증할 수 있으면 해당 TC를 선택해 재실행합니다.

확인할 조건이나 결과가 달라졌다면 부족한 부분만 추가합니다. 같은 기능의 TC라도 시험하는 입력값·상태·관찰 대상이 다르면 새 요구사항을 모두 확인하지 못할 수 있습니다.

이름이 비슷한지만 보는 것이 아니라, 기존 TC의 실제 절차와 기대결과를 변경 요구사항과 비교합니다.

6 Agent 3 · 자동화 구현과 실행

TC 기반 자동화 구현과 실행

Agent 2가 작성한 TC의 조작 순서와 기대결과를 그대로 사용합니다. 프로그램이 실제 화면에 연결해 자동화 코드를 만들고, 검사 후 시험·결과 확인·원래 상태 복원을 수행합니다. 별도 AI 검토는 TC와 화면의 연결을 확인하며, 잘못 판단할 가능성도 남아 있습니다.

새로 들어온 변경 요구사항 · 설명용 예시

“냉방은 20°C 아래로 내려가지 않게 해 주세요.
난방은 기존 16°C 하한을 유지해 주세요.”

기존 온도 변경 TC가 있어도 새 기준을 그대로 확인할 수는 없습니다. 무엇을 새로 시험하고, 무엇을 다시 확인할지 나눠야 합니다.

기존 SRS설정 온도 16~30°C

기존 TC도 이 범위를 기준으로 작성

새 요청냉방 20~30°C · 난방 16~30°C

냉방 하한은 변경 · 난방 기준은 유지

  1. 바뀌는 범위를 구분

    냉방의 최저 온도는 20°C로 바꿉니다. 난방의 16°C 하한과 두 모드의 30°C 상한은 유지합니다. 요청하지 않은 알림이나 버튼 비활성 조건은 추가하지 않습니다.

  2. 새 TC와 기존 TC 비교

    냉방 20°C에서 감소 버튼을 눌러도 20°C가 유지되는 시험이 필요합니다. 난방은 17→16°C 설정이 계속 가능한지 확인합니다. 기존 TC가 이 조건을 확인할 수 있으면 재사용하고, 부족한 부분은 새로 작성합니다.

  3. 요청한 기준으로 판정

    TC에 정한 시점에 제어 패널·장비 카드·내부 값을 확인합니다. 예를 들어 냉방 시험에서 19°C로 내려갔다면 새 요구사항과 다른 결과입니다. 제품의 현재 동작에 맞춰 기대값을 바꾸지 않습니다.

  4. 복원·보고 후 사람 결정

    시험 준비를 시작하기 전 상태로 되돌아왔는지 확인하고 결과를 보고합니다. 시험이 통과해도 자동 등록하지 않습니다. 사람이 SRS 변경안과 관련 기존 TC를 비교해 추가·대체·미등록·보류를 결정합니다.

26개 중 21개에 각 5점 · 전체 평가 완료는 아님

정상 사례여서 실패 원인 분류 1개는 해당 없음입니다. 원본 점수표의 단계 연결·승인 관련 4개는 점수가 확정되지 않았습니다(미평가 3개·검토 필요 1개). 후속 로컬 대조는 별도로 남겼으며 원본 점수는 바꾸지 않았습니다. 사람 판단과의 대조도 남아 있습니다.

10 결과와 배운 점

실무 적용 가능성과 한계

반복 작업을 연결하는 것과, 새로운 요청을 믿고 맡길 수 있는 것은 다른 문제였습니다.

가상 환경에서 화면 조작·관찰값 기록·복원·결과 전달을 한 흐름으로 수행했습니다. 시험마다 따로 정리하던 결과와 근거를 함께 확인할 수 있도록 했다는 점에서, 반복 QA 업무의 자동화 가능성을 확인했습니다.

반면 온도 요청에서는 냉방의 제품 불일치를 찾아 보고했지만, 난방은 TC와 실행 순서가 맞지 않아 시험하지 못했습니다. 결과를 숨기지 않고 알리는 기능은 필요하지만, 그것만으로 정상 요청을 처리하지 못한 문제가 해결되지는 않았습니다.

실무에 적용하려면 실제 제품·장비 환경에서 확인하고, 다양한 새 요청에서도 판단 기준이 유지되는지 사람의 판단과 대조해야 합니다. 현재는 지원하는 가상 중앙제어 범위에 한정되며, 수동 대비 시간 절감과 사람의 개입 감소는 아직 측정하지 않았습니다.

3 주요 개선 사항

테스트 설계와 실행 기준 통일

실제 AI 실행이 중단된 기록을 검토해 반복되는 원인을 찾았습니다. 특정 모드나 온도만 통과시키는 예외 대신, 같은 문제가 생기는 처리 과정을 수정했습니다.

TC와 자동화의 기준 통일

문제 설계한 시험을 실행 단계가 다시 작성하면서 값이나 확인 대상이 어긋났습니다.

수정 내용 Agent 3가 시험 내용을 다시 작성하지 않고, Agent 2의 조작 순서·기대값·확인 시점을 그대로 사용하도록 수정했습니다.

수정 후 검사 실제 화면에 맞게 연결했는지, 필수 검사가 빠지지 않았는지는 계속 확인합니다.

TC 전달 방식 · 잘못된 연결을 막는 회귀검사 코드

정상 TC를 차단하던 검사 개선

수정 전 표현·분류 차이와 중복 표기 때문에 정상 초안도 중단되는 경우가 있었습니다.

수정 후 표현 제한을 줄이고 대상·값·필수 검사·근거가 유지되는지 확인합니다. 기대값과 필수 검사에 대한 확인은 유지했습니다.

테스트 통과와 공식 등록 분리

문제 통과한 TC를 계속 추가하면 기존 TC와 기준이 충돌할 수 있습니다.

처리 방법 사람이 기존 TC와 비교해 추가·선택한 TC 대체·미등록·보류를 결정합니다. 자동으로 중복을 확정하지 않습니다.

상황별 처리와 복원 확인정상 시험뿐 아니라 제품 불일치 검출·보류·승인 선택을 로컬에서 확인했습니다. 반복 횟수와 확인 범위는 아래 결과 요약에서 구분합니다. 여러 처리 경로를 확인한 결과이며, 위 수정만의 효과나 새 AI 생성 성공률은 따로 측정하지 않았습니다. 프로젝트2 · 결과 범위와 표 보기 ↗

10 결과와 한계

자동화로 수행한 작업과 남은 한계

지원하는 시험에서는 화면 조작·관찰값 기록·복원과 결과 전달을 프로그램이 수행했습니다. 실행 결과와 근거가 한 보고서로 모이고 Slack·Notion에 전달돼, 시험 후 기록을 옮기는 작업까지 연결할 수 있었습니다. 다만 중간 보완에 들어간 시간도 있어, 수동 대비 시간 절감과 사람의 개입 감소는 아직 측정하지 않았습니다.

기준을 정해도 남는 해석 차이

온도 요청의 난방 TC처럼 준비 절차의 해석 차이로 시험하지 못한 경우가 있었습니다. 이번에는 재작성 구조를 더 늘리기보다, 실행 가능한 시험과 미실행 항목을 나누어 마지막 보고까지 전달했습니다. 실패를 알리는 것과 정상 요청을 자동 처리하는 것은 다르며, 후자의 안정성은 더 확인해야 합니다. 준비한 입력의 로컬 통과율은 새 모델 출력의 정확도가 아닙니다. 저장된 온도 사례 1건은 10월 9일 AI 검토 후 제품 불일치·복원·보고까지 확인했습니다. 새 분석·TC 생성부터 시작한 전체 흐름은 아닙니다. 해당 결과 보기 ↗

지원하는 기능

전원·모드·풍량·온도·잠금의 변경 요청을 대상으로 합니다. 새 기능 추가·삭제, 다른 웹사이트의 자동화, 제품 전체 회귀 테스트는 지원 범위 밖입니다.

가상 환경의 한계

실제 장비 통신·물리 예외는 검증하지 않았습니다. PDF 읽기는 로컬 실험이며 업로드 후 자동 실행에 연결한 기능은 아닙니다.

과거 시연과 현재 구현

영상과 공개 결과는 당시 기록입니다. 과거 잠금 사례에는 최신 복원 성공 표시가 없고, 일부 진행 사례에는 질문 원문 누락이 남아 있습니다. 현재 전달 검사를 보완했어도 과거 결과를 바꾸지는 않았습니다.
