01 · Purpose & background

변경 요청마다 반복되는 QA 업무에서 출발했습니다

실무에서는 요구사항이 바뀌면 기존 TC에서 영향받는 부분을 찾고, 필요한 시험을 추가한 뒤 결과와 수정 이력을 정리했습니다. 변경의 의미를 판단하는 일과, 반복해서 조작하고 기록하는 일이 함께 있었습니다.

확인하고 싶었던 것

반복은 AI에, 판단은 사람에게

AI와 자동화가 조작·기록을 맡으면, 사람은 변경의 타당성과 결과 검토에 더 집중할 수 있을까?

실무에서 겪던 문제

기준이 사람마다 달랐습니다

같은 요구사항이라도 담당자에 따라 넣는 경계값·회귀 TC가 달랐습니다. 기준이 문서가 아니라 경험에 있었습니다.

그래서 목표를 "TC를 많이 만드는 AI"가 아니라 요구사항부터 실행 결과까지 같은 기준을 유지하고, 근거 없는 판단을 막는 흐름으로 잡았습니다. 실제 회사 자료 대신 직접 만든 가상 중앙제어 시스템과 예시 요구사항을 사용했습니다.

03 · Hardest problem

기준을 정해도 AI의 해석은 달랐습니다

가장 어려웠던 것은 자동화가 아니라, 사람에게는 당연한 QA 기준을 AI가 같은 뜻으로 따르게 만드는 일이었습니다.

사람에게는 "하한과 상한을 확인하세요"면 충분합니다. AI에게는 무엇을, 몇 개, 어느 시점에 확인하라는 뜻인지까지 적어 줘야 했습니다. 기준을 전달하려고 시도한 과정입니다.

01
양식과 검토 기준을 자세히 정했다→ AI가 요구사항의 값을 바꿔 썼습니다(18~30°C → 16~30°C). 원문 값과 분석 값을 프로그램이 직접 대조하도록 바꿨습니다.
값 왜곡
02
단계마다 기준을 반복해서 줬다→ 같은 요구사항을 분석·설계·실행 단계가 다르게 해석했고, 기준을 잘게 쪼개자 정상적인 작성 차이까지 막혔습니다. 이미 정한 원문과 시험 내용은 프로그램이 그대로 넘기고, AI는 새 판단만 맡게 했습니다.
해석 차이
03
그래도 사람만 아는 기준이 남았다→ 10-15 온도 범위 변경 실행의 TC는 AI 검토를 통과했지만, 사람이 보니 필수 시험 3개가 빠져 있었습니다. 지침에는 "변경 후 하한과 상한을 확인"이라고만 적혀 있었습니다.

06 · Agent 3 · 자동화 실행

TC 기반 자동화 구현과 실행

Agent 2가 작성한 TC의 조작 순서와 기대결과를 그대로 사용합니다. 프로그램이 실제 화면에 연결해 자동화 코드를 만들고, 시험·결과 확인·원래 상태 복원을 수행합니다.

기존 온도 TC가 있어도 새 기준을 그대로 확인할 수는 없습니다. 무엇을 새로 시험하고 무엇을 다시 확인할지 나눠야 합니다.

새 요청냉방 20~30°C · 난방 16~30°C냉방 하한만 변경 · 난방 유지
01바뀌는 범위 구분냉방 최저 온도만 20°C로. 난방 16°C 하한과 30°C 상한은 유지. 요청하지 않은 알림·비활성 조건은 추가하지 않음
02새 TC와 기존 TC 비교냉방 20°C에서 내림을 눌러도 20°C 유지, 난방 17→16°C 적용 확인
03요청한 기준으로 판정패널·카드·내부값 확인. 실제로 냉방이 19°C로 내려갔고, 기대값을 제품에 맞춰 바꾸지 않고 불일치 후보로 보고
04복원·보고 후 사람 결정시험 전 상태로 되돌린 뒤 보고. 통과해도 자동 등록하지 않음

이 요청은 Checkpoint 1~4를 재작성 없이 통과해 끝까지 실행됐습니다. 다만 사람이 확인해 보니 TC에 필수 시험 일부가 빠져 있었습니다(03 참고). 제품은 아직 요청대로 바뀌지 않아 냉방 불일치는 예상된 결과입니다.

시험 전 확인과 문제 발생 시 처리
TC대로 시험하는지 확인실행할 수 없는 TC는 따로 보고시험 실패와 준비 오류 구분
준비·조작 순서·기대결과·복원 절차가 TC와 맞는지 확인. 다르면 시험을 막고 이유를 남김 자동화할 수 없는 조작은 제외하고 이유를 기록. 호출·내부 오류면 추가 AI 호출 중단 초기 상태를 확인한 뒤 시험하고, 복원에 실패한 환경에서는 후속 시험을 계속하지 않음
끝까지 실행한 기록 · 전원 정지 요청 (2026-10-09, 사람이 TC를 고치지 않음)

  • 강풍 표시 TC(TC-V2-001)와 중풍 표시 TC(TC-V2-002)는 사람 승인으로 공식 등록됐고, 다음 요청에서 기존 회귀 TC로 재사용됩니다.
  • 등록 직전: 최종 실행·자동 검사 통과와 필수 증거, TC·자동화 코드·실행 증거가 원본 기록과 같은지, 비교한 TC 목록이 바뀌었는지, 제품 화면 파일이 바뀌었으면 현재 화면에서 재검증.
  • 관리 중인 회귀 자산: 기준 6건(난방 적용, 송풍 온도 비활성, 제습→냉방 복원, 잠금 명령 차단, 오류 장비 차단, 30°C 상한) + V2 승인 2건, 환경 점검 별도.

09 · Practical use

실무에 적용할 수 있을까?

반복 작업을 연결하는 것과, 새로운 요청을 믿고 맡기는 것은 다른 문제였습니다.

업무판단근거와 조건
정해진 TC 실행·관찰 기록·복원 확인적용 가능준비한 상황 100/100, 복원 65/65. 화면 요소·내부값 읽는 방법은 제품마다 준비 필요
결과 분류와 보고서 작성적용 가능제품·자동화·환경·미실행을 규칙으로 분류. 결함 확정은 사람
기존 TC 재사용 판단조건부절차·기대결과 비교로 초안 제시. 같은 시험인지 최종 판단은 사람
새 변경 요청의 TC 설계초안 수준그 유형의 기준이 규칙으로 정리돼 있을 때만. 정리 전에는 필수 시험이 빠짐(10-15)
기준이 없는 새 유형을 맡기기아직 아님사람이 먼저 기준을 찾아 적어야 함. 반복 일관성 측정 전

도입하려면 필요한 것

  • 도메인 기준 문서화 — 담당자 머릿속의 경계값·회귀 기준을 규칙으로 정리하는 시간. 가장 큰 비용입니다.
  • 제품별 실행 연결 — 화면 요소와 내부값을 읽는 방법, 시험 전 상태 기록·복원 방법
  • 사람 검토 시간 — 설계 초안 검토와 최종 등록 판단은 줄지 않습니다
  • API 비용 — 10-15 실행은 생성·검토·재채점까지 호출 16회, 사용량 기준 약 $1.9 추정(청구액 아님)

현재는 가상 중앙제어 범위에 한정되며, 수작업 대비 시간 절감과 사람 개입 감소는 아직 측정하지 않았습니다.
