01 · Problem

판단보다 조작과 기록에 시간이 더 들었습니다

중앙제어 시스템을 검증하며, 요구사항이 바뀔 때마다 기존 TC에서 영향받는 부분을 찾고, 시험을 추가하고, 결과를 정리하는 일을 반복했습니다.

반복 작업을 AI에 맡기되, 변경의 타당성과 결과 판단은 사람에게 남길 수 있는지 확인하고 싶었습니다. 다만 AI에 맡기면 새 문제가 생깁니다.

위험

근거 없는 기대값

"자동 모드 18~30°C"를 AI가 16~30°C로 바꿔 쓰면 이후 TC와 시험이 모두 틀린 기준으로 진행됩니다.

위험

모호함의 전파

설계 단계의 모호한 TC가 자동화와 보고까지 이어지면, 실패 원인을 제품 탓으로 오해하게 됩니다.

회사 자료 대신 직접 만든 가상 중앙제어 제품과 예시 요구사항을 사용했습니다.

02 · Approach

단계마다 관문을 둔 파이프라인

입력은 변경 요청, 기존 요구사항(SRS), 기존 TC입니다. 각 단계는 앞 단계가 정한 기준을 다시 쓰지 않고 그대로 전달받습니다.

  1. Agent 1 · 요구사항 분석 (AI)요청을 SRS와 대조해 바뀌는 조건, 유지할 조건, 정보 부족을 나눕니다.CP1 · 원문 값과 분석 값 대조
  2. Agent 2 · TC 설계 (AI)기존 TC로 충분한지 비교하고, 부족한 시험만 새 TC로 작성합니다.CP2 · 근거·절차·기대결과 검토
  3. Agent 3 · 자동화 실행 (AI + 프로그램)TC를 화면 요소에 연결하고, 검증된 계획만 Playwright 코드로 변환해 시험한 뒤 원래 상태로 복원합니다.CP3 · TC와 실행 계획 일치
  4. Agent 4 · 결과 보고 (규칙 기반)제품 불일치·자동화 문제·환경 문제·근거 부족·미실행으로 분류해 Slack·Notion으로 보고합니다.CP4 · 집계·근거·보고값 일치
  5. 사람 승인결과와 기존 TC를 비교해 SRS 개정, TC 추가·대체, 미등록, 보류를 선택합니다.
03 · Decisions

설계하면서 정한 네 가지

1. AI가 판단할 것과 프로그램이 전달할 것을 나눴습니다

처음에는 단계마다 양식을 자세히 주면 일관될 거라 기대했지만, 같은 요구사항을 단계마다 다르게 해석했습니다. 그래서 이미 정한 원문과 시험 내용은 프로그램이 그대로 넘기고, AI는 새 판단이 필요한 부분만 맡게 했습니다.

2. 실행하지 않은 것은 통과로 세지 않습니다

핵심 정보가 없으면 질문을 남기고 멈춥니다. 자동화할 수 없는 TC는 비슷한 기능으로 대신하지 않고 제외 사유와 함께 보고합니다.

3. 시험 후에는 시험 전 상태로 되돌렸는지 확인합니다

상태를 바꾸는 시험은 준비 전 값을 기록하고, 끝난 뒤 화면과 내부값이 돌아왔는지 비교합니다. 복원에 실패하면 이후 실행을 멈춥니다.

4. 공식 등록은 사람이 결정합니다

자동 검사 통과는 등록 조건의 하나일 뿐입니다. 사람이 검토서에서 SRS 개정과 TC 등록 여부를 고릅니다.

06 · What I found

자동 검토를 통과해도 빠진 것이 있었습니다

10-15 실행의 TC는 AI 검토(CP2)를 통과했지만, 사람이 다시 보니 필수 시험 세 가지가 빠져 있었습니다.

  • 냉방 31°C 차단 시험 없음 (새 상한 바로 위 값)
  • 냉방 20°C 적용을 준비 단계에서만 하고 기대결과 없음
  • 난방 17°C에서 냉방으로 바꿀 때의 동작을 질문하지 않음
보완 · 사람이 확정한 범위 변경 규칙(바뀐 경계는 적용·차단을 각각 시험, 범위 밖 값의 전환 동작이 미정이면 질문 등)을 TC 작성·검토 지침에 추가했습니다. 새 실행에만 적용하고 과거 기록은 바꾸지 않았습니다. 이 규칙을 AI가 실제로 지키는지는 다음 실행에서 확인합니다. 누락을 숫자로 확인한 과정은 프로젝트2에 있습니다.

같은 실행에서 보고서 문제도 찾았습니다. 냉방 TC가 실패하자, 같은 TC 안에서 통과한 30°C 확인까지 검토서에 "개별 판정 미확인"으로 남았습니다. 지금은 실행 로그의 항목별 관찰 기록을 읽어 "통과(관찰값 30)" / "불일치(관찰값 19)"로 나눠 표시합니다.
