# Project1 Agent Quality Evaluation Framework

## 저장소 사용 시 참고

코드·평가 기준·개선 이력을 관리하는 저장소입니다. `evaluation-runs/`의 실제 실행 원본과 환경변수 파일은 Git에 포함하지 않습니다. 문서에 연결된 로컬 Run·JUnit·대시보드의 저장 실행 목록은 새로 복제한 환경에 없을 수 있습니다. 결과가 없다는 이유로 예시 데이터를 실제 평가 결과로 표시하지 않습니다. 프로젝트 1의 최신 작업본과 평가 당시 고정 커밋도 구분합니다.

2026-10-05 코드·문서 정리에서는 사용자 요청에 따라 로컬 `portfolio/` 페이지와 전용 `tests/test_portfolio.py`를 공개 대상에서 제외했습니다. 아래 포폴 파일 링크는 작성 환경의 로컬 검토 자료이며 새로 복제한 저장소에는 없습니다. 실행용 대시보드(`src/eval_harness/web/`)는 평가 기능에 포함되며, 포폴 사이트 공개 배포와는 별개입니다.

## 무엇을 평가하는가

평가자는 문장 수가 아니라 실제 조작 순서의 누락을 보고, TC 설명 부족과 코드·실행의 부족을 구분하도록 안내합니다. [해석 보완과 개발 비교 예시](improvements/IMP-004-judge-interpretation-boundaries.md)는 실제 모델 성능이나 사람 승인 정답이 아닙니다. 최신 확인 범위는 인계 문서를 참고합니다.

프로젝트 2는 **프로젝트 1의 Agent 1~4 전체 흐름을 같은 조건에서 반복하고, 각 단계 결과와 연결을 평가**하기 위한 도구입니다. TC나 최종 보고서 하나만으로 전체 품질을 판단하지 않습니다.

평가 자료 보완의 목적은 P1 결과를 정해진 기준으로 정확히 읽는 것입니다. P1 대신 TC를 고치거나 실패를 자동 PASS로 바꾸지 않습니다. 요청·산출물·코드·실행 증거와 평가자 오판을 구분하며, 기준 준수와 같은 조건에서의 일관성을 확인하는 목표를 유지합니다.

평가 대상은 실제 모델 기반 `../qa-agent-pipeline-v2`입니다. `../portfolio_export`의 V1 Fixture 기반 Workflow Prototype은 초기 평가기 검증용 기준 자산으로 구분합니다.

```text
프로젝트 2: 입력·기준·시작 상태·예산 준비
  → 프로젝트 1: A1 분석 → A2 TC 설계 → A3 실행 연결·코드·실제 시험 → A4 분류·보고
  → 프로젝트 2: 평가할 자료 전체 사전 점검 → A1 / A2 / A3 / A4 각각 평가 + Checkpoint·단계 연결 확인
  → 회차 결과 보존 → 같은 조건으로 다음 회차 → 예정 5회 비교·사람 검토
```

이 흐름의 **실행·수집·역할별 평가 연결기는 구현했고, 실제 API로 생성한 결과에서 기존 TC 재사용·실제 시험·Agent 4 보고까지 완료한 사례를 확보했습니다.** 최초 전체 흐름의 Judge는 응답 검증 오류로 중단됐지만, 이후 같은 저장 Run의 네 역할 평가 응답을 확보해 원문과 대조했습니다. 기존 자산 부족·평가 자료 부족·평가자 오판을 구분하며, 전체 흐름 합격·평가자 교정·5회 반복 완료를 뜻하지 않습니다. 신규 TC 생성·Agent 3 모델 계획 경로와도 구분합니다. [역할별 종합 검토](improvements/REV-001-reuse-flow-role-evaluation.md)와 인계 문서에서 최신 결과를 확인할 수 있습니다. 정상 경로의 Checkpoint와 관련 기존 TC 실행은 [실행 계획](docs/11_RELIABILITY_EVALUATION_PLAN.md)에 설명합니다. 전체 흐름이 주 시험이며 Agent 단독 시험은 원인 분석을 위한 보조 시험입니다.

## 먼저 읽을 문서

페이지의 제목·26개 기준·조건·예시·후속 안내는 쉬운 문장으로 설명합니다. `portfolio/plain-language.js`는 화면 설명용이며 실제 평가 기준을 바꾸지 않습니다. 전문 원문과 과거 평가 이유는 별도 펼치기에 그대로 남깁니다. 기준을 바꾸면 쉬운 설명도 함께 대조해야 합니다.

로컬 결과 조회 페이지는 [portfolio/index.html](portfolio/index.html)입니다. 파일을 직접 열거나 `python -m http.server 8872 --bind 127.0.0.1 --directory portfolio`로 확인합니다. 첫 화면은 Agent 1~4·공통 기준·연결 기준의 여섯 행이며, 질문·주요 항목·선정 이유와 원본 평균을 함께 보여줍니다. 평가 전 항목은 대시로 표시하고 부분 평균의 반영 범위를 남깁니다. 아래에서 실행 결과 숫자 3개·문제 목록을 확인합니다. 각 행의 세부 기준 버튼 또는 하단 펼치기로 전체 26개 항목의 세부 기준·점수 근거를 확인합니다. 현재 기준 2.5와 원본 점수의 평가 기준 2.2를 구분하며 새 점수로 재계산하지 않습니다. 시험 내역 70칸도 별도 펼치기에 보존했습니다. 기존 런타임 대시보드·평가 로직은 변경하지 않았으며 [수정 전 차트 화면](portfolio/backup-charts-20261004/index.html), [이전 대시보드](portfolio/backup-dashboard-20261004/index.html)와 [소개형 페이지](portfolio/backup-story-20261004/index.html)를 보존했습니다. 열어도 API를 호출하지 않고 자동 갱신·공개 배포하지 않습니다. 작성·검증 범위는 [IMP-006](improvements/IMP-006-portfolio-evidence-presentation.md)에 기록했습니다.

평가에서 발견한 문제와 P1 수정·재평가 증거는 [평가 기반 개선 이력](improvements/README.md)에서 관리합니다. 발견 주체와 로컬 검사/실제 API 재평가를 구분하며 과거 실패 기록은 보존합니다.

페이지의 ‘추가 확인’은 최신 코드의 시험용 등록 후 재사용 결과입니다. 과거 자산관리 표나 AI 점수에 합산하지 않으며 [별도 결과와 한계](portfolio/local-verification.json)를 함께 보존합니다. 최신 전체 검증과 준비 상태는 인계 문서에서 확인합니다.

‘실패를 제대로 구분하나요?’에서는 정상 동작·제품 불일치 검출·검사 누락 사본을 비교합니다. Agent 3와 공통 기준의 AI 평가만 별도로 보여주고, 펼치면 항목별 점수와 프로그램 검사 결과를 확인할 수 있습니다. [비교 데이터](portfolio/a3-comparison.json)에 자료 종류·평가일·원본 해시를 남겼습니다. 가상 사본을 실제 제품 실행으로 세거나 과거 26항목 점수를 덮어쓰지 않습니다.

‘최신 확인’은 위 AI 비교와 별개인 저장 전원·온도 실행의 **프로그램 평가 3항목**입니다. 제품 실패를 정확히 검출·기록한 경우 제품 결과와 Agent 평가를 구분해 보여줍니다. [최신 로컬 비교 데이터](portfolio/latest-local-comparison.json)에 원본 해시와 평가 범위를 남겼으며, 이번에 평가하지 않은 23항목이나 과거 점수를 채워 넣지 않습니다. 새 모델 평가·동일 조건 반복·공식 승인은 별도입니다.

## 네 역할을 각각 확인

| 대상 | 평가 내용 |
|---|---|
| Agent 1 | 요구사항의 수치·변경/유지 조건·미정 범위·질문·분석 근거 |
| Agent 2 | 기존 TC 재사용 판단, 누락 없는 설계, [사용자 TC 기준](benchmarks/v2/TC_REFERENCE.md)의 상세한 조작·기대결과·복원 |
| Agent 3 | TC 실행 정의/계획 → 컴파일 코드 → 실제 시험의 연결, 관찰 위치·시점·값, 복원·증거. 과거 모델 계획 경로와 현재 결정론적 연결을 구분 |
| Agent 4 | 규칙 기반 결과 집계·실패 분류, 근거 연결, 미정/미실행·다음 행동 보고 |
| Checkpoint·전체 연결 | 잘못된 결과 차단과 정상 결과 과잉 차단, 인계 누락·변조·오류 전파·승인 경계 |

제품 시험 FAIL과 Agent 평가 FAIL은 다릅니다. 실제 불일치를 정확히 검출·보고했다면 해당 역할 기준은 충족할 수 있습니다. 중간 차단으로 실행되지 않은 역할은 미실행이며, 기존 TC 재사용으로 필요 없는 신규 계획 생성은 근거 있는 해당 없음입니다.

## 현재 구현 범위

`full-flow-0.12`는 이번 예산으로 평가할 역할들의 입력을 모두 준비하고 크기·민감정보 검사를 마친 뒤 Judge를 호출합니다. 준비 오류가 있으면 해당 묶음의 Judge 호출을 시작하지 않으며 P1의 품질 실패로 바꾸지 않습니다. 이 사전 점검은 이미 수행한 P1 생성 비용까지 없애지는 않습니다. 예산 밖 역할은 미평가로 남기고, 저장 자료의 단일 역할 평가도 유지합니다. 대시보드는 P1 실행 상태와 P2 평가 중단 이유를 구분합니다.

요청·SRS는 해당 Run의 저장 파일과 `run_manifest.json`의 파일명·해시를 대조합니다. 해시가 없는 과거 자료는 원본 연결 미확인으로 표시하고, 기록된 해시와 다른 자료는 평가 준비를 중단합니다. 이 해시는 원본 연결 검사이지 내용의 정답 보장이 아닙니다. 알림 파일도 폴더에 있다는 이유만으로 전달됐다고 표시하지 않고, 검증된 전송 기록에 연결되어 실제 평가 입력에 들어간 경우만 포함으로 기록합니다.

수집기는 단계별 최종 결과뿐 아니라 검토·오류·선택/제외·재작성 기록과 당시 승인 TC 목록을 해당 역할에 전달합니다. 최상위 폴더와 후보별 폴더의 A3 계획을 모두 읽고 비교 자료에도 포함합니다. 초안만 있으면 초안, 상태만 있으면 `STATUS_ONLY_NO_FINAL_ARTIFACT`로 구분하며 실행 성공으로 바꾸지 않습니다. `trace.evidence_delivery`에는 JSON별 전달/부분 전달/로컬 보존 여부를 남깁니다. 크기 제한으로 JSON을 조용히 건너뛰지 않고 준비 오류로 알리며, 다른 Run·입력 요청 불일치·연결 파일과 승인 TC 목록의 해시 불일치는 차단합니다. 실제 호출 원문이 없는 단독 P1 기록은 호출하지 않은 것이 아니라 원문 미확보로 표시합니다.

Agent 4 평가에는 최종 보고 JSON과 함께 같은 실행의 Slack·Notion 안내 자료를 제공합니다. `external_reporting.json`이 연결하는 보고서·Checkpoint·알림의 해시와 실행 번호를 확인하고, 기존 원문을 그대로 전달합니다. 자동 검사 결과인 CP4에는 실행 번호가 없으므로 최종 보고서의 해시 연결로 확인합니다. 알림 생성(PREVIEW/DRY_RUN)과 실제 전송·수신·사람 승인은 구분합니다. 안내 자료가 없으면 확인 불가로 남기며, 일부 JSON의 빈 확인 목록만으로 사용자 안내 전체가 없다고 판단하지 않도록 안내합니다. 다른 실행·변조·잘못된 파일 연결은 평가 준비 오류로 중단하고, 기존 전송 크기·민감정보 검사를 그대로 적용합니다. 과거 평가 입력과 점수는 자동 갱신하지 않습니다.

자동화 코드 본문은 AI 평가 입력에서 제외합니다. 실행 기록·생성 manifest가 가리키는 파일의 해시는 계속 로컬에서 확인하며, AI에는 파일 식별 정보만 제공합니다. A3-03은 프로그램이 같은 실행의 TC 검사 번호·계획·실제 관찰값·결과를 대조합니다. 자동 코드 생성기의 동작은 P1 로컬 회귀검사로 확인하고 AI의 매번 코드 읽기를 대신합니다. TC·계획의 의미 보존과 실행·복원 완료 주장은 AI 평가에 남습니다. 로그 수집의 파일당 24,000바이트·합계 40,000바이트 제한과 출처·경로·민감정보 보호는 유지합니다. 역할별 평가 본문은 근거 번호를 붙인 UTF-8 JSON 기준 최대 250,000바이트입니다. 이는 프로젝트의 자체 입력 예산이며 모델의 토큰 한도·요금 한도가 아닙니다. Preview에 본문 크기·한도·시스템 지침을 포함한 요청 JSON 크기(출력 스키마 제외)를 표시합니다. 초과하면 내용을 자르거나 자동 분할 호출하지 않고 중단합니다. 과거 기록에 구조화 관찰값이 없으면 새 점수를 만들지 않습니다. [담당과 한계](docs/12_DETAILED_RUBRIC.md)를 참고하세요.

평가는 기존 26항목을 유지한다. full-flow-0.6는 A4 집계·증거 연결 두 항목을 파이썬으로 채점하고 모델 질문에서 제외한다. 전체·상태별·제품/환경/고정 사례 수량과 요구사항·출처 연결을 원본 실행 행에 대조한다. 저장/전체 실행은 같은 정보 부족·질문 보존 검사를 사용한다. 공식 승인 E04는 무승인 변경 위반을 확인할 수 있지만 승인 전후 증거 없이 통과 점수를 만들지 않는다. 나머지는 AI 중심/혼합 평가이며 E01~E03의 자동 모델 호출은 없다. score-0-5-v2는 PASS 4~5점, FAIL 0~3점이다. 과거 v1과 무점수 기록은 그대로 보존한다. 대시보드는 평가 항목 수·평가된 항목 평균 /5·미평가·위반을 함께 보여주며 완성도/정확도 점수로 표현하지 않는다. 사람 교정과 실제 모델 점수 품질은 미검증이다. [채점 기준·분담·집계 방식](docs/12_DETAILED_RUBRIC.md#05점-채점)을 참조한다.

평가 AI는 복잡한 경로와 인용문을 직접 작성하지 않고, 프로그램이 자료 값마다 붙인 근거 번호를 선택합니다. 프로그램은 해당 번호를 원래 자료 위치·원문으로 연결하고 기존 인용·항목·적용 조건 검사를 수행합니다. 없는 번호·중복 번호·다른 패킷의 응답은 거절하며, 과거 응답을 자동 보정하지 않습니다. 번호의 존재는 판단의 의미 정확성 증명이 아니며 사람 검토가 계속 필요합니다. 긴 문서 문자열은 값 전체가 하나의 근거 단위이고 문장별 의미를 자동 판별하지 않습니다.

역할 평가에는 생성 요청 본문을 유지하고 근거 검토 요청/입력의 중복 본문은 원본 해시로 구분해 제외합니다. 단, 저장 검토 입력에 있는 기존 TC 목록과 실행기 복원 사실은 `retained_reference_context`에 원문 그대로 보존해 단독 실행 자료에서도 참고할 수 있게 합니다. 이 자료가 API 요청 자체나 실행 성공 증거인 것은 아닙니다. 호출 기록·검토 결과·재작성·Checkpoint 기록은 유지하며 전체 원본은 로컬 증거에 보존합니다. 제외된 본문의 의미까지 평가했다고 주장하지 않습니다. 전송 크기 한도와 호출 예산은 유지합니다. 새 번호 방식의 실제 모델 검증 상태는 인계 문서를 확인하세요.

중복 자료는 기존 공통 처리로 정리합니다. 비교할 `context`와 `artifact`는 직접 읽을 수 있게 유지하고, 다른 위치의 충분히 큰 동일 값만 원래 위치를 참조합니다. 비슷한 문장을 같은 내용으로 합치거나 실패 기록을 삭제하지 않습니다. 한도를 늘려도 큰 자료는 여전히 중단될 수 있으며, API 호출 승인 전에 크기와 필요한 근거를 확인해야 합니다.

공통 전송 안전검사는 JSON 문자열을 해석한 실제 내용에도 적용합니다. 줄바꿈 이스케이프를 파일 경로로 오인하지 않도록 하되 원문과 전송 내용은 바꾸지 않습니다. 실제 경로·키·HTML 차단은 유지하며, 중복 JSON 필드와 검사 깊이 64단계 초과는 안전하게 중단합니다. 완전한 JSON이 아닌 문장은 기존 문자열 검사로 확인합니다. 이 검사는 민감정보 패턴 검사이며 모든 정보 유출을 탐지한다는 보장은 아닙니다.

P1의 생성·Checkpoint 재작성·근거 검토 호출을 모두 기존 P1 호출 한도에 포함합니다. 별도 P2 Judge 예산은 유지합니다. 신규 계획이 필요 없는 기존 TC 재사용은 계획 생성 기준만 ‘해당 없음’으로 처리하고 실제 시험·복원 증거는 계속 평가합니다. 현재 역할 패킷은 `role-rubric-2.5`이며 이전 패킷으로 새 평가를 실행하려면 다시 생성해야 합니다. TC-R06에 SRS 개정의 필요성과 전체 인수기준 셀의 미변경 조건 보존을 포함합니다. 과거 결과는 수정하지 않습니다. 최신 P1 작업본과의 로컬 연결 검사는 실제 API 전체 실행 성공과 구분합니다.

2.4에서는 TC-R05의 제목·조건·예시를 ‘요청 조건의 검증 범위 충족’으로 맞췄습니다. 상태 전환·조회도 평가하며, 범위 제한에 필요한 경계·명시된 예외 검사도 유지합니다. 점수 자동 보정이나 P1 로직 변경은 없으며, 이 안내가 실제 모델의 비적용 오판을 줄이는지는 아직 미검증입니다.

새 평가 자료의 `context`와 `artifact`는 원문 그대로 직접 표시하고, 다른 자료의 반복 이력만 같은 값의 참조로 줄입니다. TC의 구조화 복원 확인은 계획 명세로 평가하되 실제 누락·잘못된 비교 기준은 지적합니다. TC-R05는 정상 범위도 평가하고, A4-02는 원본에 분류할 신호나 보고의 원인 주장이 없을 때만 비적용입니다. 자료 부족은 미평가이며 원본 점수는 자동 보정하지 않습니다. 저장 전원 사례의 후속 평가에서 A3 복원 확인 오반려와 A4 적용 범위는 해당 응답에서 개선을 확인했지만, A2 TC-R05는 정상 전환을 다시 비적용으로 판단해 미해결입니다. 다른 사례·반례와 반복 안정성은 남아 있으며 최신 결과는 인계 문서에서 구분합니다.

새 결과에는 실제 사용한 평가 기준·평가자·모델을 기록합니다. 서로 다른 버전의 결과를 섞은 묶음은 평균을 만들지 않되 항목별 점수·위반·미평가는 유지합니다. 버전 정보가 부족한 과거 결과도 원본 그대로 읽으며 반복 평균 비교에는 사용하지 않습니다. 이 집계 보완은 저장 응답 대조와 로컬 회귀 검사로 확인했습니다. 같은 버전의 비교는 유지하고 화면용 메타데이터 비공개 처리 후에도 원본 버전으로 비교합니다. 실제 모델 판단의 정확도·반복 안정성 검증과는 구분하며 최신 근거는 인계 문서에 있습니다.

| 경로 | 할 수 있는 일 | 아직 하지 않는 일 |
|---|---|---|
| `run-v2` | V2 저장 기록의 구조·해시·값·집계·일부 시나리오 조건 및 23개 상위 역할 표시 | 새 제품/모델 실행, 전체 의미 판정 |
| `repeat-self-test` | 모의 5회 호출·오류·중복·누락·집계 검사 | 프로젝트 1 실제 반복 실행 |
| `judge-openai` | 수동 준비한 A1~A4 또는 별도 E2E 패킷의 Preview, 승인 후 모델 평가, 출력 계약 검사 | 자체 전 단계 자동 수집·5회 실행 연결 |
| `full-flow` | 버전 고정·독립 사본·A1~4 연결·호출 한도·증거 수집·역할 평가·기록 비교 | 최초 일괄 Judge는 중단, 저장 Run의 후속 역할 평가와 구분. 같은 조건 반복·사람 교정·신규 계획 및 실패 경로 평가는 남음 |
| 대시보드 | 저장 V2 평가·전체 실행 기록·평가기 자체 검증을 구분해 조회 | 화면에서 유료 실행 시작 안 함 |

26개 세부 기준은 정의와 역할별 입력에 연결돼 있습니다. 필수 자료 키가 있다는 사실이나 평가기 테스트 통과를 실제 의미 정확성으로 해석하지 않습니다. 평가 모델의 사람 정답 교정과 전체 Live 반복 평가는 남아 있습니다.

## 현재 사용할 수 있는 명령

### 전체 흐름 Preview · 실제 호출 없음

```bash
python -m eval_harness full-flow --target ../qa-agent-pipeline-v2 --spec benchmarks/v2/full_flow.example.json
```

예시는 1회 리허설 명세입니다. P1 호출 최대 10회(생성·CP 재작성·근거 검토 합산), 별도 역할 평가 최대 4회이며 이 명령 자체는 전송하지 않습니다. 실제 전송·비용 승인 후 같은 명령에 `--execute --approval-sha256 PREVIEW_HASH`를 붙입니다. P1 요청당 출력 최대 12,000토큰, 평가 요청당 최대 6,000토큰이며 SDK 자동 재시도는 0입니다. 기존 명세의 `generation` 예산 필드에 근거 검토도 합산하며 프로젝트 1의 제한된 CP 재작성 정책은 유지합니다.

실행 기록은 `evaluation-runs/FLOW-.../`에 저장합니다. 5회 시험은 별도 명세와 예산 승인이 필요합니다. [전체 실행 사용법과 한계](docs/11_RELIABILITY_EVALUATION_PLAN.md#10-전체-실행-연결기-사용법)를 먼저 확인하세요.

최대 3회 제한 명세는 `full_flow.three-call-pilot.json`입니다. 생성·재작성·근거 검토 합산 최대 3회, Judge 0회로 전체 상한을 유지합니다. 이 한도로 전체 단계 완료를 보장하지 않습니다. 해당 파일로 바꿔 Preview를 확인할 수 있지만 새 실행에는 새 사용자 승인이 필요합니다. 이전 3회 승인을 재사용하지 않습니다.

### 역할별 평가 Preview

```bash
python -m pip install -e ".[judge]"
python -m eval_harness judge-openai --packet benchmarks/v2/role_packet.example.json --model MODEL_ID --role-rubric
```

`MODEL_ID`를 사용할 평가 모델 ID로 지정합니다. 명령 기본값은 전송 미리보기이며 API를 호출하지 않습니다. 예시 패킷은 합성 Agent 2 자료이고 실제 전달 이력이 없어 일부 증거 누락이 표시됩니다. 이를 Agent 2만 평가하는 전체 계획으로 해석하지 않습니다.

공통 2개를 포함해 A1 6개·A2 10개·A3 5개·A4 4개 기준을 적용합니다. 전체 연결기는 일부 E2E 코드 대조를 수행하며 의미 충분성·Checkpoint 오탐/미탐 평가는 남아 있습니다. 사용자 정의 일부 항목 패킷은 `--role-rubric` 없이 사용할 수 있고 `CUSTOM_SUBSET`으로 구분합니다. 실제 유료 호출은 전송 내용·예산 승인 후에만 수행합니다. [사용법과 한계](docs/11_RELIABILITY_EVALUATION_PLAN.md#8-openai-평가자-연결).

### 모의 반복 및 저장 기록 검사

```bash
python -m eval_harness repeat-self-test --trials 5 --scenario value-drift
python -m eval_harness run-v2 --target ../qa-agent-pipeline-v2
python -m eval_harness run-v2 --target ../qa-agent-pipeline-v2 --dataset benchmarks/v2/scenario_v1.jsonl
```

모의 시나리오는 `normal`, `value-drift`, `same-wrong`, `missing`, `transport-error`, `duplicate`입니다. 원본·호출 이벤트·오류와 JSON/HTML을 별도 `evaluation-runs/`에 보존합니다. 모의 명령 종료 0은 자체 시험 완료이지 Agent 품질 합격이 아닙니다.

저장 기록 경로는 과거 Run 3개를 읽으며 30개 시나리오 전체 실행이나 새 독립 Trial로 세지 않습니다. [명시 조건 검사](docs/10_SCENARIO_ORACLE.md)와 [TC 직접 검토](benchmarks/v2/TC_REFERENCE_REVIEW.md)는 한정된 근거입니다. `run-v2`는 자동 위반이 없어도 의미 검토가 남으면 REVIEW(종료 코드 3)이며 FAIL은 2, ERROR는 4입니다. 결과 HTML은 직접 열어 봅니다.

### 보존한 V1 평가기 검증 경로

```bash
python -m eval_harness behavior-self-test
python -m eval_harness run --suite project1-audit --mode fixture
python -m eval_harness run --suite known-good --mode fixture
python -m eval_harness dashboard --port 8766
```

대시보드 기본 포트는 8765이며 프로젝트 1 UI와 겹칠 수 있어 위 예시는 8766을 사용합니다. 첫 화면은 **저장 평가 요약 → 사례별 A1~4·전체 연결 → 펼치는 검사 근거** 순서입니다. 평가기 자체 검증은 별도 탭이며, 그 경로의 95%/90% Gate를 실제 Agent 품질 기준으로 승계하지 않습니다. [화면 사용법](docs/06_DASHBOARD_GUIDE.md)을 참고하세요. 개발 Case 목록과 한계는 [Benchmark Card](docs/03_BENCHMARK_CARD.md)를 확인하세요.

[초기 저장 검사 베이스](docs/07_V2_EVALUATION_BASE.md)와 [과거 재평가](docs/09_PROJECT1_REVIEW.md)는 역사적 기록이며 현재 성능으로 합산하지 않습니다.

프로젝트 1 원본·SRS·공식 TC·포트폴리오는 변경하지 않습니다. 반복 시험 중 Notion/Slack 게시·사람 승인·공식 등록은 자동 수행하지 않습니다. 생성 결과·평가 결과·제품 시험·사람 승인 권한을 분리합니다.
